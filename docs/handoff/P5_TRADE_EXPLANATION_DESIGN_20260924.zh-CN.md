# P5：给通用贸易报告接入模型解释（实施规格）

## 目的与现状

用户问“大豆出口最近怎样”，系统已经能先确认商品、方向、月份和数据版本，再查已核验的月度数据，生成图表、数值表及来源。模型解释尚未接入：`trade-query-v1` / `trade-query-both-v1` 的 `ai_status=not_run` 是准确的现状。此阶段只增加**可选的、针对同一份数据报告的文字解释与人工审阅**。不把金额波动写成已证实的政策因果，也不恢复原项目的因果识别目标。

第一版的成功路径是：用户确认范围 → 数据报告立即可读 → 用户主动点“生成解释” → 服务端只调用一次已配置模型 → 原答保存、按证据合同校验 → 页面展示“待审阅” → 用户逐项核对 → 已采纳文字附在这份报告上。模型失败不妨碍阅读数据报告；短连接成功不等于完整报告成功。

## 为什么单独接线

- 现有 `/api/session/task/explanation/*` 只接受 `program-report-a3` 和 `temporal-report-v1`。`public-brief-explanation-v1` 要求 `public-report-v1` 的观察/指标结构；不能仅把通用贸易报告改个 `kind` 来复用。
- 旧 `provider_executor.py` 是冻结实验及14槽账本，不用于日常产品。复用的是 `.local/product-model.json` 的配置、`OpenAICompatibleModel` 底层调用，以及旧流程“先领取、原答先落盘、未知结果不自动重试、逐项审阅”的控制方法。
- `/api/trade/report` 目前只返回内存 JSON，浏览器仅把结果放在 `localStorage`。要防止刷新、换报告或双击时串答，必须先有服务端不可变报告记录。

## 锁定的对象与接口

1. `/api/trade/report` 保持原有确定性字段，同时新增随机 `report_id` 与 `report_sha256`。服务端把完整确定性报告和哈希保存在项目级 `.local/trade-reports/`；原始月包、加工 CSV 不复制入记录。哈希只覆盖原报告本体，不包含随机编号、解释或审阅。每次新报告生成新编号，旧记录保留供核查。
2. 新增只读 `GET /api/trade/report-state?report_id=…`，从服务端读取该编号对应的原报告、解释状态及已保存的审阅；页面刷新以它为准，不把浏览器存储的报告或审阅视为权威。编号必须通过格式与目录边界检查；记录损坏、哈希不符或所需文件缺失时拒绝。
3. 新增 `POST /api/trade/explanation/call`，请求仅包含 `report_id` 与期望的 `report_sha256`。服务端锁内核对它仍是该报告且状态为 `not_requested`，先持久标记 `provider_call_started`，再读**产品专用配置**并调用一次；不回退到旧实验 `.local/glm.json`。记录所选服务商/型号、配置摘要、请求摘要、返回摘要、用量和失败类别，绝不记录或回传密钥。重复点击/并发/服务重启后的 `provider_call_started` 一律不自动再发请求。
4. 模型成功返回后先保存原文与 SHA，再解析。明确的 HTTP 4xx 参数/权限拒绝记 `failed`；超时、断线、进程中断、结果无法确认记 `unknown_outcome`；无论哪类，同一编号都不重试，用户可明确创建新报告。解析失败记 `invalid_answer`，保留原文，不将其显示为已核实结论。
5. 新增 `POST /api/trade/explanation/review`：输入报告编号、报告摘要、原答摘要、逐项 `accept` / `reject` / `needs_revision`、理由和 `facts_checked`。服务端验证条目顺序、摘要及当前修订号；至少一项采纳且所有项已有最终判断才有 `reviewed` 状态。已采纳解释仅回填当前编号的报告；后续审阅修订须保留旧记录，不能覆盖原始回答。

以上端点都沿用现有本机同源 JSON 入口、请求大小门和安全错误处理。模型调用必须由用户显式触发，不随打开报告或刷新自动发生。暂不把通用报告硬塞进旧 session 任务状态机，不改旧政策案例与评测冻结记录。

## 模型读什么、写什么

从服务端保存的原报告生成 `trade-data-explanation-v2` 输入，不信任客户端传入的数字。输入包括原问题、进口/出口方向、商品组/编码、伙伴国、月份、指标定义、各月金额/记录状态、程序计算的最新月与上月变化、来源 URL、数据版本及报告摘要。为每个**已经实际算出**的观察给稳定 ID，例如 `import.latest`、`import.month_change`、`export.period_total`；缺值不造观察。月度观察会明确给出程序计算的“增加／减少／持平”。双方向两套观察分开，不造“贸易顺差”或相减后的数。

模型输出为一个 JSON 对象，含协议版本、报告摘要和至多六条 `{observation_id, text}`。`observation_id` 必须来自本次输入，每条文字长度受限；不得补入新的数字、日期、税率、商品编码或网址。数字由程序报告展示，模型只用自然中文解释已有变化的含义、尚不能判断的原因与下一步需查看的资料。禁止把金额称为数量、把相关变化写成政策因果、写投资建议或确定性预测。解析器负责结构、ID、长度和显式越界词检查；**不能假装代码已经验证文字的全部经济含义**，人工审阅负责最后的事实判断。若用户问“为什么变了”，解释须明确现有金额数据不能单独辨别价格、数量或政策作用。

新合同只影响通用贸易查询；旧政策解释合同、已有模型横评题包及分数不改。模型文字在审阅前明确标为“模型草稿”，正式打印/导出默认只取已采纳条目；数据图表始终可查看。

## 预算、验收与停止

- 输入仅包含本份报告的最多12个月×进出口两组必要事实；不发送全量数据库或旧实验题包。调用前记录实际请求字节数，设置上限，超限不删证据硬发请求。输出上限先按短结构化解释设为 2,048 tokens；实际供应商兼容性与用量以真实返回核对，未知价格不编造。连接测试与完整报告测试分开记。
- 离线替身验收：大豆进口、出口、两者；玉米或明确编码；单月/缺月；旧编号与新报告串用；服务端报告被改；模型乱编数字/来源、无效 JSON；HTTP 400/401、超时及未知结果；双击并发仅一个调用；重启后不重复；逐项审阅、刷新恢复、旧审阅与新报告不能串用。旧政策案例回归照跑。
- 页面验收：先看到图表和真实口径，AI 另行点击；等待/失败/未知/待审阅/已审阅五种状态清楚；每条解释旁有对应事实和来源；窄屏与打印可读。报告可以比现在更详细，但模型不能取代确定性数值表。
- 真实模型验收在离线链通过后才做一份代表性完整报告，保存问题、数据版本、代码版本、请求参数、原答、响应型号、用量、耗时与人工逐项判断。成功与否如实记录；不把本次开发题并入旧四题正确率，不因失败临时改门槛或自动重试。

## v3 实施：围绕用户的问题写一段有用的解释

### 2026-09-24 离线收口

已按下方规格完成实现，细节见[本轮执行记录](runs/20260924-P5-DIRECTION-V3-OFFLINE.zh-CN.md)：

- 程序从月度行计算连续走势、区间高低及并列，不跨缺月或未观察月份；真实大豆出口资料确认 2026-01 为高点，随后连续 6 个月减少，2026-07 为低点。
- 按问题只将相关程序观察送入新协议；每个方向只接受一段解释，可在一段中关联多个事实。
- 报告在模型调用前展示走势事实；页面可读取新数组引用和旧单一观察ID。
- Python 定向回归 28 项、页面离线流程 3 项通过；本轮 0 次模型 API 调用。真实模型文字是否自然、是否真正解释清楚，尚未验证。

遵照“先完成产品，再做模型测试”的顺序，v3真实调用留到整体界面收口后，届时至多新建一份报告做一次受控验证；不重放旧答案，也不把一次结果称为准确率。

### 为什么不能只删掉两段套话

v2 的真实回答把“最新月”“比上月变化”“期间合计”各解释一遍；报告上方已经展示这些数字，重复解释自然显得空。可是用户问“最近有什么变化”，只留下“比上月减少”也会漏掉多月走势。真实大豆出口记录显示：当前可查的 2025-08 至 2026-07 共 12 个月中，2026-01 的月度金额最高，此后连续 6 个月下降，2026-07 为区间最低；最新月较上月少 3,500,150 美元。这些都是月度金额的描述，不是政策效果或下降原因。

下一版让程序先把问题对应的观察算清楚，在调用模型之前就给用户看一张“这段时间发生了什么”的事实卡；模型再用一小段话解释其含义。图表、金额和来源继续由程序呈现；模型无需逐项复述每个数字。

### 程序要提供的事实

- 对完整、连续的月度区间，计算最新月与上月差额，以及截至最新月同方向连续变化的月数。至少连续两个比较方向相同，才写“连续”；只有一次变化时只说“较上月增加／减少／持平”。遇缺月、非已观察值或月份不连续，在缺口处停止，不跨过去数连续月份。
- 区间最高、最低只从本次已观察的月份计算；区间不完整时须限定为“已观察月份”，不能称“整段期间最高／最低”。如多个月并列，须写“并列”。所有结论明确绑定商品、进出口方向、伙伴国、指标和所选月份。
- 对“最近有什么变化／走势”生成一个聚焦的走势观察：包含最新月方向、连续变化的事实，以及有证据时的区间高低点。金额和月份在程序事实卡显示。单月或不可比较时明确说资料不足，不编造趋势。
- 现有 `latest`、`month_change`、`period_total` 观察 ID 保留供旧记录展示；新走势观察使用独立 ID。旧 v1/v2 原答及审阅记录保持原状。新报告的模型请求和解析使用新的协议版本，不把旧答重算成新成绩。

### 按问题选择解释内容

| 用户问法 | 模型须解释的程序观察 | 报告保留的确定性展示 |
| --- | --- | --- |
| “最近有什么变化／走势怎样” | 每个方向一条走势观察；无可比较月份时改用最新月观察并说明不足 | 所选期间的月度图、最新月差额、完整金额表 |
| “这一段累计多少／合计多少” | 期间合计；区间不完整时不造合计 | 月度图与各月金额 |
| “最新一个月是多少” | 最新月金额的统计含义 | 精确金额、商品与指标口径 |
| 同时问进出口 | 进口、出口各选对应观察，各写一段 | 两套图表和各自来源；不直接相减 |
| 问“为什么”或政策效果 | 先回答可观察的变化，再说明金额数据不能识别原因 | 所需的数量、价格、目的地或政策资料缺口 |

若一个问题明确包含两类需求，可各选一条；不能因为原报告有三个观察就强制解释三个。为免两条观察变成两段重复文字，新协议的每条解释包含 `observation_ids` 数组及一段 `text`，每个方向至多一条。例如同时问最新月金额和走势时，一段文字关联 `export.latest` 与新的走势观察。解析须核对所有选中 ID 恰好出现一次、同一条内方向一致、没有无关 ID；逐项审阅仍以解释条目为单位。页面读取旧记录时继续识别 v1/v2 的单个 `observation_id`，新记录显示数组对应的事实。既有数字、日期、税号、网址禁令和人工审阅继续适用。

模型请求只提供选中的程序事实、适用范围及来源信息；完整月度行留在数据报告和图表中。这样模型无须自行从原始行重新找走势。输出为每个方向一条 `interpretations`，每条 `text` 控制在 20 至 160 字，并避免对每条事实重复解释统计口径；用户问原因时，只需一次说明金额数据无法识别原因。某类问题所需事实不存在时，程序应在调用前说明数据不足，不改用无关观察凑回答。解析负责结构和事实编号，经济含义仍需人工核对。

### 给用户看的样子

本例的程序事实卡应概括为：“在这 12 个月里，美国大豆月度出口金额于 2026 年 1 月最高，之后连续 6 个月下降；7 月为区间最低，比 6 月少 3,500,150 美元。”模型的一段解释可以像：“这几个月确实一直在往下走，不只是最新一月出现变化。至于原因，仅凭出口金额还看不出来；需要再看出口数量、价格和目的地。”后一段只是目标文风的人工示例，不是模型实测答案。完整图表、原金额及来源链接仍在报告里，待审阅时能看到对应事实。

### 原定实施与验收要求

1. 在通用贸易解释模块中独立计算走势观察，按问题确定所选观察，并用新协议发送与解析。`trade_report_store.py` 应将程序事实随报告状态提供给页面；`web/design-preview/live.js` 在模型尚未调用时就展示焦点事实，收到解释后在同一处附上可审阅文字。保留原始数据报告、报告摘要、单次领取和原答先保存的流程，不建立另一套金额计算。新旧回答使用各自保存的协议形状显示，旧记录不重新解析。
2. 离线用例覆盖：大豆 12 个月的 6 连降与末月最低；连续上涨、持平、只有一次变化、并列高低、单月、缺月、未观察值、进出口双方向和不相关观察被拒。核对程序事实直接来自月度行，不能靠模型猜趋势。
3. 页面用离线替身跑“提问→确认→图表→单段解释→审阅→刷新”；确认默认阅读视图没有三段重复提醒，旧 v1/v2 报告仍可打开。新协议的更改不得回写旧冻结结果。
4. 若离线验收通过，再用同一发布数据版本、新报告、同一问题与相同服务商做最多一次开发验证。以 v2 已保存原答为对照：必须答出最新月方向和多月走势，不能出现无依据原因、无关合计或重复限制；结构通过后仍需用户评价可读性。输出预算上限沿用 2,048 tokens，费用未知不估价，超时或结果不明不重试；本设计阶段 API 调用为 0。
