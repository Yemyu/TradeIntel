# 产品收口顺序与模型测试约定

2026-09-21 用户最新决定。本文件覆盖旧计划中“立即做模型排名”“先做前端”“把手动模型模式作为产品交付”的安排；历史成绩与失败记录不改写。本次只是更新计划，不表示代码已收口或模型已通过。

## 1. 顺序与停止扩张

1. **先收口现有核心产品**：核查并补齐政策导入/确认、数据覆盖与计算、证据检索、模型输入输出接线、审阅与报告导出、受控更新、持久化与失败恢复。用现有接口、脚本及必要的旧页面检查，不开始前端重设计。
2. **再做统一模型验收**：核心输入输出约定稳定后，冻结同一四题、证据和评分规则，按需测试候选；期间常规单元/集成/反例检查不停。聊天模拟只作开发参照，正式模型成绩必须来自独立、同题、同证据的实际模型调用。后续真实接口验证是自动产品交付的一部分，不能被聊天测试代替。
3. **最后做前端展示和使用体验**：模型合同稳定后，用户提供参考网站，从中共同选合适模板，做一个统一网站的首页/工作台/报告页。现在不选模板、不新增展示页面、不先行改版。复用现有后端，不为界面重建业务框架。

当前状态：核心集成已完成并通过相关离线回归；前端模板和真实 API 仍按上述顺序留待后续。具体接线结果见[核心收口方案](CORE_CLOSEOUT_DESIGN_20260921.zh-CN.md)。

目标不变：官方新贸易政策→商品与条件→真实贸易数据→有证据的经济解释→中文报告→人工审阅导出与受控更新。不恢复自研因果识别，不新增多智能体/微调/数据库来凑技术点；保留MySQL、已有数据、下载ZIP及原始课程目录。没有删除或提交推送授权。

## 2. Luna在这里扮演什么角色

- 开发默认用用户在当前聊天选择的 **Luna最高推理** 做模型回答模拟，节约额外API费用。需要时明确请用户切换；不能声称已自动切换。
- 模拟尽量使用产品实际准备的问题、证据、提示及输出合同，保存原始输出，再交给同一解析/校验路径。未经核查不得声称现有代码已具备完整模拟导入链。
- 这是开发测试方式，**不是要求最终用户导出任务包再手工粘贴答案的产品方案**。不因此新建一套手动模式前端。
- 聊天中运行GPT不意味着本机部署了模型，也不意味着获得了应用API。模拟不能验证真实接口鉴权、网络、超时、流式输出、费用或端点兼容性；同一聊天含项目历史时，也不是严格独立基准。
- 最终使用/交付文档仍说明配置API后由应用调用模型。需要真实API验证时说明具体用途与调用上限，由用户提供可用接口；当前不启动真实调用、不索取密钥。
- 对话模拟、程序stub、真实API结果分开记录；模拟不占用真实API账本，不解除已停止实验，不写成真实调用或真实接口准确率。

## 3. 后续候选与统一评测

- Luna最高是默认开发参照，不是已证明通过的生产推荐，也不预先认定它的能力排名。
- 用户后续可能提供Qwen、GLM、DeepSeek等可用接口；具体型号、推理模式、端点、资源包是否适用届时核实。“免费”以实际账户与配置为准，不对整个系列作保证。
- 候选使用同一四题、相同证据和评分规则；每个确切型号选一个明确配置，记录推理档位。开发样例与最终四题分开，不反复改同题直到通过。
- 不默认穷举所有型号或推理档；按资源逐批选择并预先定调用上限。此前“首轮必须SOL+Qwen、最多8答”不再是当前执行命令。
- 展示重点为型号/配置、测试数量、整题通过数与比例、主要问题；同时标明测试渠道。聊天已看过答案或历史错误的示例只作开发记录，不进公平排名。4/4只是小样本验收，不是普遍100%正确。

## 4. 下次执行入口与验收

下一步先回读代码和运行记录，形成一张简短的“已贯通/尚有缺口/本轮补齐”清单，然后集中完成一条真实核心链，不再不断新建实验阶段。优先核查：解释模块是否已接到持久任务、审阅、导出；新公告确认及覆盖是否实际绑定；失败/重启能否恢复；启动说明是否可复现。不得把待核查项直接当作已发现缺陷。

核心收口的证据：确定性计算可复算，范围/来源/版本一致，结构化模拟回答经正式校验和审阅到导出，缺证/坏输出/中断明确失败且不冒充核准报告，已有测试失败逐项说明。阶段结论分别报告“核心工程完成情况”“前端未完成项”“真实模型/接口未验收项”，不把前者等同整个产品完成。

模型分工：Astra中负责复杂接线设计、风险判断与最终审查；规范锁定后Luna最高实施、文档和常规测试。新阶段开始按用户规则报告模型建议；出现方法冲突停止扩大修改并回到Astra。
