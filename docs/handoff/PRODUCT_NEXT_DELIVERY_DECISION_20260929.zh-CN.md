## 结论

第一版仍按既定定位交付：**本地运行的美国商品贸易研究助手**。自然提问后由用户确认商品、进出口方向和已发布月份；程序读取已核验数据，生成图表、金额、来源和限制。模型解释是另行点击、需要人工审阅的试用入口。手工导入新公告与商品报告是另一条受控路径，不宣传自动找政策或判断政策因果。

不把“继续公告阅读 v4 的第三次真实调用”当作本地版收口前置条件。v4 已通过离线合同与页面反例，但没有新公告上的模型语义成绩；此前两份未见公告的正式结果仍是 `invalid_response/answer_contract`。商品解释 v4 的三道开发题有返回且结构通过，但相对页面的阅读增益是 0/3，第四题按规则未发。**这不能推出所有模型都没用，也不能把现有 AI 描述为稳定的自动研究员。** 公告阅读后续若继续，应先锁新官方材料、答前参考和人工对照，再另获单次调用许可；不重发已见两案。

## 为什么先做本地交付

- [发布决定](PRODUCT_RELEASE_DECISION_20260925.zh-CN.md)及[交付范围](DELIVERY_SCOPE_20260927.zh-CN.md)已有明确的本地边界。现有 `/preview/` 能走商品确认→数据报告→可选解释/审阅；[干净克隆与完整依赖验收](runs/20260927-FULL-INSTALL-QA.zh-CN.md)在本机 macOS 新虚拟环境、另附数据包的条件下复现过三类报告和服务重启读回。
- 普通 Git 克隆**不含** 124 个贸易数据文件（约 579 MB）；目前仅有本机约 64 MiB 的 ZIP，[快速上手](../LOCAL_RUN.zh-CN.md)注明无公开下载地址。推送源码或打开静态 GitHub Pages 都不能让别人在线调用本地 Python 服务；公网还缺鉴权、密钥隔离、HTTPS、存储和运维决策。
- MySQL 是已对账的 SQL 副本，不是页面运行依赖；不为“看上去像正式产品”而临时换成云库。持续自动下载新月份/新政策也未交付。
