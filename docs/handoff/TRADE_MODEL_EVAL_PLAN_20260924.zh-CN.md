## 先说测什么

产品先由程序确认商品、贸易方向和月份，查询已发布数据，计算图表与走势。模型只给同一份报告补一小段解释；原答要经过格式检查和人工审阅才可采纳。模型不是在选择商品编码、计算金额或证明政策因果。因此分开验收：

1. **产品链**：用户能否从自然提问走到正确的官方商品范围、真实报告、可选解释和审阅。错误商品、错误方向或缺数据属于产品问题，不能记成模型答错。
2. **模型解释**：在完全相同、事先固定的报告和消息下，各配置能否返回合规、切题、有帮助的文字。使用当前 `trade-data-explanation-v3`，不能借用旧 `public-brief-unified-v2` 的解析器或分数。
3. **阅读效果**：图表和数据由程序提供；审阅者判断新增解释是否真的让普通读者更懂，而不只是重复数字或堆叠“不能判断”。结构合法不等于内容合格。

旧成绩仍可在[历史模型对照表](runs/20260923-MODEL-COMPARISON-TABLE.zh-CN.md)单独展示。GPT-5.6 对话旧 v1、旧政策 v2 API、通用商品 v1/v2 冒烟和本次 v3 均不是同一考试，不能混成一个准确率。

## 先修一个已发现的产品问题

只读检查与本地查数曾发现：自然问法“最近美国乘用车进出口情况怎么样？”会被误判为**只看出口**，因为旧识别只匹配连续的“进口”“出口”。现已修复“进出口／进/出口”识别并回归；独立本地页面实际输入该问法，确认页选择进口与出口，数据报告分别出现两方向数值，未调用模型。另保留“大豆和咖啡”多商品须澄清的回归，不允许静默挑一种。[离线执行记录](runs/20260924-TRADE-V3-EVAL-OFFLINE.zh-CN.md)。

| 首轮候选 | 渠道与推理设置 | 运行前必须核对 |
| --- | --- | --- |
| GPT-6 Luna / max | Codex 全新独立会话，手动基准 | 菜单确为 GPT-6 Luna、max；相同题包，无本项目历史答案。不是产品 API 成绩 |
| GPT-6 Sol / high | Codex 全新独立会话，手动基准 | 菜单确为 GPT-6 Sol、high；与 Luna 同材料。单列对话渠道 |
| DeepSeek `deepseek-flash` / thinking enabled + high | API，当前产品优先候选 | 记录请求名、返回名、推理参数和日期；短连接成功不等于完整报告通过 |
| GLM `glm-4.6v` / 生产兼容的默认推理设置 | API，条件候选 | 当前产品配置**没有 GLM 高推理档位**；不得把默认值写成已验证的 high。若要指定 high，先核实官方接口并另版接线、预检 |
| DeepSeek `deepseek-v4-pro` / thinking enabled + high | API，条件候选 | 先核实当日是否为与 Flash 可区分的后端版本及账号可用性；只回显别名时明确“不确定”，不宣称独立 Pro 成绩 |

GLM-4.5-Air 历史上按用户决定停止；千问也已取消本轮，不因过去给过密钥就自行重启。GPT 的 Codex 对话不需用户提供 API key，但 Codex 的工具与系统环境不同于裸 API；结果与 API **分渠道陈列**，不混排行。OpenAI 官方资料确认 GPT-6 Luna 支持 `max`、Sol 支持 `high`；如果以后要做 GPT 的**产品 API**对照，需单独接入并验证，不能把 Codex 对话冒充产品请求。[官方模型页：Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Sol](https://developers.openai.com/api/docs/models/gpt-6-sol)。DeepSeek 当前官方 Chat Completions 文档列出 `deepseek-flash`、`deepseek-v4-pro` 及 `reasoning_effort` 取值；实际后端快照仍以运行时能核实的信息为准：[官方接口文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

独立评测执行器应复用现有 HTTP 适配与 v3 解析方法，但不循环修改 `.local/product-model.json`，不经网页对同一 `report_id` 重复调用。产品报告记录的“一份报告最多领取一次”继续保持；评测用隔离账本和冻结消息逐配置发送。密钥只从本机受保护配置／环境读取，不写入题包、日志或 Git。

## 评分、预算与停止

每份原答分别记：①接口是否返回完整结果，②原答是否通过 v3 结构／引用／字数／方向／新增数字守卫，③事实是否忠于本报告，④是否答到用户问题，⑤是否有具体解释增益且自然可读。第三至第五项用隐藏模型名的原答、对照独立事实卡逐项审阅；AI 辅助审阅须标明，用户未亲自确认时不写“人工已采纳”。严重错误如答错商品/方向、编造原因、把金额当数量、投资建议，一题即不通过；纯粹“不足以判断”而不解释已观察走势也不通过。

每模型按 T1→T4 同序、每题至多一次。重大事实错误、结构失败、超预算或未知结果触发停止，余题记 `not_run`；已返回的坏答案记失败，接口无原答单列故障。**不自动重试、不改原答补分、不用正式题改提示**。若产品材料本身错，该题所有候选同版结果作废，修复后另建版本。只对完成同四题的配置比较 `通过题数/4`；提前停止的配置列“已答/计划、通过/已答、未跑”，不据此断言模型总体高低。

单次产品型请求沿现行上限：消息不超过 60,000 字节、`max_tokens=2048`、原答不超过 20,000 字节、解释每方向 20—160 字；总时长拟设 90 秒，执行前确认评测器确实限制**总时长**而非仅 socket。真实 API 最多一次大豆开发调用；正式首轮至多 3 个 API 配置 × 4 题 = 12 次完整调用，条件候选不满足前置门即少于此数。短连接预检另记实际次数与用量。费用未知不估价；每个配置记录输入、输出、推理 tokens、耗时及能核实的花费，未返回用量写“未知”而非 0。超时或中断结果未知时不重试。

发布报告分两栏：模型解释 `Q/R`（Q 是整题通过，R 是已保存原答）；产品整链 `D/N`（自然提问到审阅可读报告的完成数）。解析器拦住错误是产品守卫通过，**不等于模型答对**。四道题即使全过，也只说明这版四个小样本通过，不能写“准确率 100%”或“无需人工审阅”。
