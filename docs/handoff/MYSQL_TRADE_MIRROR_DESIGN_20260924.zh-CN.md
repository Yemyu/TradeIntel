# 进出口数据的 MySQL 同版镜像：实施方案

状态：设计已定，**进口 48 月、出口 12 月均已逐行复核并写入整版验收记录**。试装与收口见 [2026-07 记录](runs/20260925-MYSQL-202607-PILOT.zh-CN.md) 和 [整版验收记录](runs/20260925-MYSQL-FULL-VERIFICATION.zh-CN.md)。本方案只处理当前已发布的美国进口 HTS10 和出口 Schedule B 月度文件；不改变网页报告的读数来源，也不重做旧政策案例。

## 要解决什么

目前报告直接读取已核验的 CSV。MySQL 的作用是保存**同一版本的可查询副本**，并证明 SQL 查询没有把金额、商品编码或缺失状态读错。完成后可以展示数据建模与 SQL 对账能力，但不能仅凭表里有记录，就说数据库已和文件一致。

当前文件版本：

| 数据 | 已加工月份 | CSV 数据行 | MySQL 明细行的预期规模 | 版本 |
| --- | ---: | ---: | ---: | --- |
| 美国进口 HTS10 | 48 | 840,463 | 1,680,926（每行拆成中国/全部来源两行） | `dd9801492e80268e51480b08c2edcbf495aba3ce01b7ee64739566f67a151ef8` |
| 美国出口 Schedule B | 12 | 3,769,576 | 3,769,576 | `4308e4a820cd86bb6a19e223b4ae887fe0a030eef4a8af0c1ce96cb8c30a4b9f` |

这是**两套**数据版本，不合成一个版本号。进口是消费进口额；出口是国产出口加再出口的 FAS 金额。HTS10 和 Schedule B 的十位码也不能直接互换。网页继续以文件快照为准，MySQL 不是新的“实时数据源”。

## 表和字段怎么定

保留 `db/schema.sql` 已有的 `trade_dataset_release`、`trade_dataset_month`、`trade_import_hts10_monthly`；旧的 `trade_monthly` 及旧装载脚本不动。先只补两张表：

1. `trade_export_scheduleb10_monthly`：每月、每个 `scheduleb10` × `partner_code` 一行；保存 `domestic_export_fas_usd`、`foreign_reexport_fas_usd`、`total_export_fas_usd`、两个 observed 标志和原包摘要。主键包含数据集、版本、年月、商品码、目的地码；外键指向 `trade_dataset_month`。金额非负；未观察到的分项存 `NULL`，观察到的零额存 `0`；两个分项至少有一个被观察到，总额必须等于两个分项中已观察金额之和。`ALL_DESTINATIONS` 是查询时对目的地求和，**不另造一条总目的地记录**。
2. `trade_mysql_mirror_verification`：每个数据集版本最多一条**验收通过记录**，保存原清单摘要、预期月份数、CSV 行数、按映射规则应有的 SQL 行数、实际核验的 SQL 行数、审计文件摘要和 UTC 验收时间。进口一条 CSV 会变成两条 SQL 行，因此这三种行数不能混为一个数字。只有全部月份逐行一致才插入；存在版本记录或月份记录本身都不表示已验收。若以后手工改了数据库，旧验收记录不能代替重新核查。

已存在的进口表维持当前列：一条 CSV 行拆为 `CHINA` 和 `ALL_ORIGINS` 两条 SQL 行。`china_observed=0` 时，即使 CSV 为便于处理写着金额 `0`，SQL 金额也必须是 `NULL`；`china_observed=1` 且金额为 `0` 则保留 `0`。导入时核对 `hts8 == hts10[:8]`，但不必在 SQL 里重复存一个可由十位码得出的字段。原 CSV 的细节行数、来源文件名保留在文件和清单中；本轮 SQL 镜像是**报告查询所需字段的等价副本**，不是声称 CSV 的所有列都搬进了表。

2026-09-25 表约束复核：`observed=1` 的分项必须显式要求金额 `IS NOT NULL`。MySQL 的 `CHECK` 会接受结果为 `UNKNOWN` 的表达式；仅写 `金额 >= 0` 时，`NULL` 可能绕过约束。[MySQL 9.7 CHECK 文档](https://dev.mysql.com/doc/refman/9.7/en/create-table-check-constraints.html)。`db/schema.sql` 已修正进口金额和出口两个分项，真实数据库尚未建这些新表。

`trade_dataset_month.row_count` 一律记原 CSV 行数，而不是拆分后的进口 SQL 行数。每月记录同时保存原包 SHA-256 和加工 CSV SHA-256；进口清单没有写入后者，应像现有 `TradeDataRepository.catalog()` 一样从实际文件计算。`trade_dataset_release.source_manifest_sha256` 是清单文件本身的 SHA-256；如果同一数据版本出现不同清单摘要，拒绝静默覆盖并人工查原因。`published_at_utc` 是本项目登记文件快照的时间，不是 Census 官方公告时间。

## 装载和验收顺序

拟新增独立命令 `scripts/mirror_trade_mysql.py`，默认只读检查；旧 `scripts/load_mysql.py --replace` **不能**用于这批数据。

1. **文件预检（不连接数据库）**：按现有两个 repository 重新计算版本；核实 60 个加工文件摘要、CSV 表头、年月、编码、原包摘要、观察标志、金额非负与行键唯一。进口每月的行数、中国金额和全部来源金额还要与清单原始汇总对上；出口每行核对 `total = domestic + foreign`，未观察分项只能为空，月行数对上清单。文件在读取前后摘要必须一致。
2. **数据库预检（只读）**：用现有 `tradeintel` 登录路径连接本机 MySQL，检查版本、数据库、`SHOW CREATE TABLE` 和可用空间。不自动启动系统服务，不要求改全局 `local_infile`，不运行旧脚本的 `TRUNCATE`。若真实表结构与预期不符，先停下来制定迁移，不依靠 `CREATE TABLE IF NOT EXISTS` 假装已经升级。
3. **小范围装载**：先各取 2026-07 一个月，按清单版本写入版本/月元数据和明细。用项目已有 MySQL 命令行客户端及批量 `INSERT`，凭据仍由登录路径提供；不把密钥放进脚本或日志。每月用一个 InnoDB 事务，禁止 `--force`、`INSERT IGNORE`、`REPLACE`、关闭外键和自动改全局 SQL 模式；预检确认会话处于严格模式。命令或连接失败后先检查数据库实际状态，不根据本地进度条猜测提交结果。首轮不用 `LOAD DATA LOCAL INFILE`：官方 MySQL 文档说明它可能把数据解释错误降为警告、对重复键采取忽略行为，不能以“命令成功”充当严格验收。[MySQL 9.7 LOAD DATA 文档](https://dev.mysql.com/doc/refman/9.7/en/load-data.html)。
4. **逐月核对**：从 SQL 按商品码/目的地码顺序流式读回，和 CSV 经过上述 `NULL` 转换后的规范行**逐行比较**；再核对行数、各金额合计、观察数量、源摘要和月份。小范围两个月通过后才扩到其余月份。读回对账是必要的，单看行数和总额可能掩盖互相抵消的错误。
5. **版本验收**：进口 48 月、出口 12 月分别全部通过后，生成带清单摘要、每月数量/合计/结果和数据库信息的审计 JSON，再插入对应的 `trade_mysql_mirror_verification`。两份验收都存在且当场重新核对通过，才报告“当前 MySQL 同版”；产品读取来源本阶段仍不切换。

遇到已存在的相同版本和月份：先完整读回核对；一致则跳过装载，不一致则**停止**，不执行 `REPLACE`、`TRUNCATE` 或自动删除。某月装载中断后不能把半成品说成已验收；后续是恢复、隔离还是清理该月，必须根据实际数据库状态单独决定。新版本只新增版本键，不覆盖旧版。

### 2026-07 单月试载的执行细则

前置只读检查已完成：本机 MySQL 9.7.0，`tradeintel` 只有六张旧表，新镜像表尚不存在；同卷约有 142 GiB 可用。项目虚拟环境没有 MySQL Python 连接库，服务器的 `local_infile=OFF`、`secure_file_priv=NULL`。因此沿用本方案已经选定的 **MySQL 命令行客户端 + 分批 `INSERT`**，无需改服务器设置或增加连接库。上一轮记录中“命令行还是连接库尚未决定”属于表述错误。

1. 新命令默认只读；明确要求试载时才执行写入。先重新运行完整离线文件审计，锁定两个版本、清单 SHA 和 2026-07 文件 SHA。数据库预检核对严格 SQL 模式、目标表是否存在，以及现有版本/月/验收记录。若新表不存在，单独运行 `db/schema.sql` 建表并检查实际 `SHOW CREATE TABLE`；已有表结构若不符，停下处理。建表与数据写入分开，因为 `CREATE TABLE` 会隐式提交事务。[MySQL 9.7 隐式提交文档](https://dev.mysql.com/doc/refman/9.7/en/implicit-commit.html)。
2. 每个方向各用一个 InnoDB 事务：插入或核对版本元数据，插入该月元数据，再把规范化的明细按不超过 200 行且 SQL 长度不超过 1 MiB 分批写入。导入字段按固定白名单生成 SQL，数据值按类型安全编码；金额空值写 `NULL`，前导零编码写文本。禁止 `--force`、`INSERT IGNORE`、`REPLACE`、自动删除及全局设置更改。只有全部行生成完且加工文件末次 SHA 仍一致，才发送 `COMMIT`；过程异常时关闭连接并重新查询状态，不能根据本地打印的进度推断提交结果。
3. 提交后单独打开只读连接，按主键顺序流式读回全部字段；当月 CSV 的规范化行也按同一主键排序，逐行比较商品码、伙伴、金额的 `NULL`/真零、观察标志、来源 SHA，任何一行不同即失败。同时查询月行数和金额/观察数汇总，核对 `MonthAudit`。进口 2026-07 预计 18,813 条 CSV → 37,626 条 SQL；出口预计 337,316 条 CSV → 337,316 条 SQL。
4. `trade_dataset_release` 仅登记文件版本；`trade_dataset_month.status='queryable_detail'` 仅说明该月明细物理上可以查询。**可信的整版完成状态只看 `trade_mysql_mirror_verification`**，单月试载不能写该验收记录，网页报告也继续从已发布文件读取。重跑时先完整读回已存在月份：一致则跳过，不一致则停止。若写入命令的结果不明，先区分“无行”“完整且一致”“不一致/部分”三种实际状态，绝不盲重试。
5. 本次试载的对照是相同 SHA 的 CSV 文件，目标为两方向逐行差异 0、行数和所有汇总差异 0、重跑不增行。预算仅限上述两个 2026-07 月份、每批最多 1 MiB、模型 API 调用 0；记录每月耗时与 MySQL 占用变化。任一结构、摘要、事务结果或读回异常立即停在当月，不扩到其余月份。两个月均通过后，才根据实测吞吐量安排 60 月全量及整版验收。

## 验收测试与止损

- 离线小样本：进口前导零编码、观察缺失与真零、重复 HTS10、错误月份/摘要；出口重复商品×目的地、未观察分项、`total` 不等于分项和、错误目的地码；同版本不同清单；中断后无验收标记；重复运行不改已验收行。
- 真实两个月：2026-07 进口与出口各一月，SQL 逐行读回与 CSV 完全一致，且清单金额/数量对账通过。之后才运行 60 月全量；**不使用模型 API**。
- 任一文件摘要、表结构、SQL 行内容、金额、观察状态或月份对不上，立即停在该月，保留审计记录，不写版本通过标记，也不把网页切到 MySQL。连接断开时不自动重试写入，先查实际已提交到哪里。
- 首月装载前观察磁盘与执行时间；若批量插入过慢，先记录实测吞吐量与失败语义，再单独评估受控的批量导入方式，不为提速临时放宽逐行核对。

## 实施边界

下一执行阶段可以先写表结构、纯离线解析/对账模块和假数据库测试；本机 MySQL 服务未运行时，不能宣布真实接通或全量完成。启动现有系统服务、修改全局配置、处理已有不一致数据，分别需要先说明具体动作再做。完成 MySQL 镜像也不等于公网部署已完成；页面目前还是本机单用户产品。
