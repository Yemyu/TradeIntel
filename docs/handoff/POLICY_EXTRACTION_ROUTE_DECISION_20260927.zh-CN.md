# 公告 AI 辅助填写：v6 之后怎么走

**执行更新：**初版离线结果见[2026-09-27 离线记录](runs/20260927-ANNOUNCEMENT-READING-OFFLINE.zh-CN.md)；[调用前判定](ANNOUNCEMENT_READING_CALL_GATE_20260927.zh-CN.md)要求的一次修订已形成 [v2 离线包](runs/20260927-ANNOUNCEMENT-READING-V2-OFFLINE.zh-CN.md)，但浏览器完整链和人工收益仍未验收。本路线仍未授权真实模型调用。

日期：2026-09-27。这里决定的是**新公告的字段建议**，不是普通商品查数和报告的整条产品链。当前没有发起新模型请求，也没有启用公告或写 MySQL。

## 结论

本版不再让 DeepSeek Flash 一次填写 13 个公告字段，也不把公告自动抽取列为发布前置条件。新公告继续走已经接通的路径：保存官方原文 → 人工核对 13 个字段及出处 → 明确启用 → 用户确认商品和月份 → 程序查已发布贸易数据并生成报告。AI 可以在以后帮助**阅读和提出少量建议**，但不能代替确认、不能自动启用，也不能把贸易额当成政策效果。

这不是把整个 AI 产品砍掉：普通商品报告的可选模型解释是另一条链；这里只暂停反复失败的“公告全文一次性填表”。因此产品仍可服务新公告，但目前需要人提供并核对公告，不具备“全网自动发现、自动读懂、自动发布”的能力，展示时必须如实说明。

## 为什么不直接改回普通 JSON

同一份已见 R2 公告此前已经做过五个普通 JSON 版本：关闭推理后虽然有正文，仍依次出现重复引文、字段类型、税号证据和顶层形状等问题，五次都没进入语义评分。strict-tool 路线又依次遇到 HTTP 400、传输合同不一致、歧义引文；最新 v6 虽得到一个工具调用，参数却不是合法 JSON。详见[五次记录](runs/20260926-POLICY-EXTRACTION-PROFILE-ITERATIONS.zh-CN.md)和[结构化传输记录](runs/20260927-POLICY-EXTRACTION-STRUCTURED-TRANSPORT.zh-CN.md)。因此“换个输出开关再试一次”没有新的验证依据。

重复试跑并没有证明公告内容无法由模型理解；它证明**当前 13 字段、18 个商品码及逐字引文同时输出的合同，对所用模型和配置不够稳定**。也不能据此断言更贵模型一定解决：目前没有同题、同合同、同人工评分的对照结果。

## 若以后恢复 AI，先验证一个更小的任务

真正不同的新假设是：不要让模型复制整段原文、列全商品码并直接产出可提交的 13 字段候选。先由程序从已保存公告生成稳定的原文位置编号和商品码**待核对清单**；模型仅针对一个小字段组写简短建议，并返回所依据的位置编号。位置必须由程序反查到原文；编号不存在、原文版本变化或内容越界都拒绝。建议只显示在人工表单旁，不能直接转成已确认候选。原有 `policy_candidates.py`、人工摘要确认和启用门不放宽。

首个开发验证只选 R2 的“税率含义、条件、例外”三项，保持原公告正文、字段参考和既有错误记录分离。先离线用人为构造的合格/畸形返回检查：短格式可解析、重复键拒绝、位置可回溯、缺附件与未知状态可保留、任何建议都不能自动提交或启用。随后**若另行批准真实调用**，冻结代码/原文/请求摘要、模型与推理档位、输出门、一次调用上限、预算和不重试规则；只发一次开发请求。JSON 解析、位置回溯和人工逐项语义检查都过关，才有理由考虑 D2；一项失败即停，不把开发题算正确率。

对照是现有人工表单与已经保存的 v6 原答；指标分开记：格式可用、位置回溯、严重事实错误、人工需改动的条目。R2/D2 是已见开发材料，H1/H2 也参与过验收设计，不能称盲测；没有独立人工复核和新材料之前，不宣传泛化准确率或省时百分比。正文中缺少附件时保留 unknown，不能从模型记忆补全。任何真实费用按服务商返回的 usage 核算，预估门不是供应商硬封顶。
