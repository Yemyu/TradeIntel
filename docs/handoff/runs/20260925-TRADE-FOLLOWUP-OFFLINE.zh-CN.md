## 2026-09-26 网络原因补查

在项目原来的受限执行环境中，不带密钥的 `curl` 和 Python HTTPS 请求都无法解析 `api.deepseek.com`；同一 Python 预检在允许联网的环境中可以到达服务端，不带密钥的 HEAD 返回 HTTP 401。结合先前 0.013 秒的失败，**本机 DNS 隔离是很可能的原因**。但先前账本没有保存底层错误，仍不能证明当时请求一定未到达服务端或一定未计费，因此保留 `unknown_outcome` 原记录。

一次性执行脚本已补上“先做不带密钥的连通检查，再预留调用名额”，并在后续网络故障中只记录安全错误类别；超出解释合同的原答也会先保存供审阅，不会悄悄丢失。实际核对：受限环境的预检明确报 `dns_error`、不预留名额；允许联网的环境预检通过。**这轮补查没有发出新的模型请求。**

追加三项离线回归：无密钥 HEAD 返回 401 算连通；DNS 失败既不写调用账本也不创建模型客户端；已有 `unknown_outcome` 时在网络预检之前拒绝重试。连同 v4 解释和模型传输的相关检查共 **30 项通过**；仍未跑全量回归。

## 2026-09-26 追问恢复尝试：服务返回空正文

网络和新凭证验证后，另建 `.local/trade-followup-dev-20260926-recovery-1/` 账本，用 `deepseek-flash` / high、温度 0、`max_tokens=2048`，对同一小麦报告问题发出 **1 次恢复请求**。约 10.3 秒后服务返回，但适配器得到的可见正文为空；账本记录 `failed / empty_response`，没有回答可评分。因当时空正文分支过早返回，服务端型号、`finish_reason`、usage 和响应 ID 都没有被保存；本次请求是否计费未知。旧 `unknown_outcome` 原账本保持不变，这次恢复尝试也不重发。

可能原因之一是高推理模式下 2048 输出上限被推理内容用完，但本次缺少 finish reason 和 usage，**不能确认**。DeepSeek 官方说明高推理内容与最终正文分开返回，`max_tokens`限制生成长度，若 `finish_reason=length`，正文可能因达到上限而不完整；这是解释方向，不是对本次响应的结论：[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)、[Chat Completions 参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)。

已修复之后的空正文记录路径：保留安全的服务型号、响应 ID、usage、结束原因和工具调用数；如结束原因是 `length`，明确记为预算截断候选，不保存推理正文、不自动重试。新增回归后，追问、v4 和模型传输相关测试共 **31 项通过**；差异空白检查通过，未跑全量回归。此修复不能补回本次已经丢失的响应元数据。随后在4096输出上限下作了单次复验，见下节。
