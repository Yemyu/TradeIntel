# 0113：先把验收保护层做成可反例测试的组件

## 结论

在 0112 审查后，先没有解冻 0111 的 24 道题，也没有调用 API。新增
`src/tradeintel_ai/prospective_acceptance.py`，把下一次前瞻验收所需的硬门槛做成
独立、无网络依赖的组件，并用合成材料写了 11 个离线反例测试。

这不是新的模型准确率，也不是 0111 已通过。它只证明：当验收材料出现明显的
基础设施故障、串改或记账缺口时，系统会停下来，而不是被“人工批准”伪装成成功。

## 已实现的保护

1. `validate_terminal` 先检查连接、超时、HTTP、结构、传输和不完整交付；即使
   审查回调返回 `approved=true`，硬失败仍不能通过。澄清/边界题到达可执行状态
   也会被拒绝。
2. `validate_structured_review` 要求总体理由、每个冻结必答点的状态和理由；数字、
   政策或引文项必须留下 witness。它只记录“已审查”，不把结构审查冒充语义正确。
3. `freeze_dependencies`/`verify_dependencies` 为显式列出的运行器、适配器、提示、
   题目、参考、语料和数据文件保留 SHA-256；每次预约外部调用前重新核对。
4. `ProspectiveCallLedger` 在进入 provider 前持久化 `reserved` 记录，返回后写入
   用量、耗时和安全元数据。用量未知、累计已报告 tokens 达到 80,000、依赖串改、
   连接/结构失败都会停止；不重试、不续跑。
5. 账本预先创建固定的问题行。停止后尚未到达的问题仍为 `not_run`，不会被从分母
   中删除；阶段预算固定为规划 24、有证据回答 8、无证据回答 8。
6. `assert_no_reference_leakage` 对合成消息检查人类专用参考值，防止把金标准偷偷
   放进模型提示。正式题目仍须在 Astra 审查时逐题检查。

## 离线验证

`tests/test_prospective_acceptance_guards_0112.py` 共 11 项通过，覆盖：

- 恶意审查通过不能覆盖 connection/structure/incomplete delivery；
- 澄清题不能被执行；
- 审查漏项和缺 witness 失败；
- 参考答案泄漏被拒；
- 原始响应和审查提交脱敏保存并绑定 SHA-256；
- 文件串改在下一次调用前停止；
- 调用预约先于假 provider 持久化；
- 失败、未知用量、80,000 tokens 都停止并保留后续 `not_run`；
- 非返回状态不能继续运行。

全套工程测试：566 项通过，0 API。
