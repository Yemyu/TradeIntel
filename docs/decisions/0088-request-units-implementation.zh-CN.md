# 0088：逐项需求清单接入

按0087实现research-plan-4。当前CLI启用require_request_units，仍复用一次规划与至多一次政策生成。旧v1–v3编程调用兼容；新CLI不接受缺少清单的旧格式，开关与源码均参与确认指纹。

request_coverage模块校验start/end为整数、逐位置引文一致、非空白原文完整覆盖、无重叠、字段和分类枚举合法。模型不得填写ID、执行状态。宿主按原文排序分配request-001等ID，与policy_question/trade_series/trade_comparison任务关联。背景及限制不能创建任务，但中文预览保留它们供用户发现误分类。

政策清单中的每一项原文须存在于最终policy_question；一个政策执行任务可关联多项需求，生成成功时仍needs_review。统一结果和中文报告记录逐需求执行状态与semantic_coverage_verified=false。没有把程序执行完成解释为模型完整回答。

出现unsupported时整份计划返回needs_scope_selection，没有执行令牌，不执行可做子集；澄清保留已识别清单和具体missing信息。纯格式/位置错误归为规划失败，不能说用户没提供信息。所有检查均在金额工具/回答调用前完成。

## 验证与边界

新增9项离线测试，全套457项通过（31.401秒），随后报告逐需求展示的针对回归亦通过。覆盖组合交付、同句两项政策要求、追加原文遗漏、份额/第二原产地超范围、政策问题漏事实、重复文字位置、具体澄清、禁止旧格式降级及确认失效。

两个限制被显式保留：模型将新增需求错误标为context，仍可通过机械检查；模型使用错误比较方向但有合法日期引文，也仍可能通过。开发测试要求其中文分类和方向可见、semantic_coverage_verified保持false，不把它们计作正确语义。否定/引述的分类同样来自模型，程序不声称理解任意否定表达。

这9项使用人工构造计划/本地数据，零在线API、零训练；不是GLM准确率。严格要求模型输出字符位置会增加生成负担，目前没有真实验证其可用性。原有政策问题仍须为原文连续片段，多项分散问题只能使用涵盖它们的连续原文，不会自动拼接新问题。
