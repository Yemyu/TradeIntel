# 0083：已确认案例设置与登记窗口元数据

日期：2026-09-11。上一阶段 0082 修复了整合入口的审计和历史指纹问题；本阶段继续完成 0080 清单中已经锁定、但尚未接线的两项基础能力。全程零在线 API、零训练/微调、零因果拟合。

## 决定

1. 把当前案例中不会由模型决定的内容登记为宿主设置：美国进口国、Section 301 List 1、资料截止日 2018-07-06、进入消费进口额、只读、`causal_effect=false`。设置有版本号和 `confirmed` 状态，并随计划和 provenance 输出。
2. 把四个登记比较窗口放进独立的金额无关元数据文件 `data/processed/analysis/registered_comparison_windows.json`。文件只保存窗口月份、解释、覆盖可比性状态、局限和来源摘要的 SHA-256，不复制任何金额。
3. 登记窗口来源先核对统计摘要的 SHA-256，再提供给比较解析器。解析器不能直接把旧统计摘要当作窗口配置接口，也不能因为窗口存在就声称因果成立。
4. 当模型明确选择登记窗口、同时把 `trade.months` 留空时，宿主才从登记元数据推导两组月份，并把规则、登记 ID、来源写进计划和 provenance。若用户已经提供月份，仍必须与登记窗口完全一致；不一致就停止并要求重新确认。
5. 确认指纹包含登记窗口元数据，因此预览后若窗口文件改变，旧确认不能继续执行。

## 为什么要这样做

“美国、哪项政策、哪个指标”属于本项目已经确认的研究口径，不应每次让模型猜。模型负责理解用户表达；宿主负责守住研究范围。登记窗口也是如此：窗口月份是研究设计参数，不是模型可以临时编造的日期。

把窗口定义与金额摘要分开，可以同时做到两点：用户能看懂窗口是怎么来的，程序又不会为了展示窗口而提前读取或复制贸易金额。来源指纹保证“窗口定义对应哪一版摘要”是可追溯的；它不等于摘要里的金额已经被本阶段重新计算。

## 仍然明确的边界

- 四个窗口都是描述性比较。`causal_effect_estimated` 仍为 `false`，不能把“同期窗口”写成关税的因果效果。
- 这不是模型训练，也不是把月份自动补全成任意日期。只有用户明确选择登记 ID 且没有冲突月份时才派生。
- 这一阶段没有完成历史范围判定修正、同页政策片段合并、完整预算/恢复交付状态，也没有启动真实语义验收。
- 因果匹配仍处于阻断状态；本阶段没有放宽门槛、没有重新拟合，也没有把描述性比较包装成因果结论。
