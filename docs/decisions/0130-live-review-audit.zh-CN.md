# 0130：真实开发审核复核与修正

日期：2026-09-13。本阶段为实现审查与缺陷隔离；0次外部模型调用。

## 结论与已复现证据

后续当前进度见[0132运行器接线](0132-runner-review-resume.zh-CN.md)：四场景与gap已接入持久化审核恢复并通过离线整链；公共live入口仍待统一接线。下文的“运行器尚未接入”属于此前交接，不再代表最新进度。

0129仅完成部分接线，不能称0128全部完成。旧 `ai_assisted_fact_review` 实际是关键词/来源页匹配，没有宿主助手读取回答：

- “生效日期不是2018-07-06，额外税率不是25%。”配上冻结引用后，两项事实均被标supported，校验器最终approved=true。
- 正确的“生效日期为2018-07-06，额外税率为25%。”在无证据B组被标成两项missing，因为匹配逻辑仍要求引用。这使对照不公平。
- 规划清单默认pass、报告只回填指纹，不能证明读懂计划或报告。
- pending审核包写入磁盘已实现，但账本仍明确resume_supported=false；回调抛错得到stopped，不能称可恢复暂停。
- 预检对虚构模型/端点也返回ready=true；它没有验证凭据、持久化完整快照或实际请求配置。

上述错误位于新0129路径。本轮没有用它请求真实模型，也没有据此撤销或重算0109等历史成绩。

## 本轮修复

撤除冒充AI审核的自动语义判定；兼容函数明确要求实际宿主判断。公共live构建/执行入口在构造模型或创建批次之前拒绝运行。预检保留四题及配置检查材料，但明确ready=false，列出三项实现缺口，并声明凭据未验证、快照未持久化、恢复未支持。此处阻塞来自尚未完成的代码，无需用户重新授权或读英文PDF。

新增反例覆盖否定、正确数字附带无根据因果断言、无证据B组、未读报告，以及执行入口零调用/零输出目录。所有自动审核入口均不得产生通过标签；这些测试证明错误认证路径被切断，不证明语义审核已经实现。

验证：定向11项通过；全套663项测试通过（40.944秒）。预检未就绪返回退出码2，不能再被脚本当作可启动凭证。

## 下一实现目标与验收边界

### 后续进度：账本与待确认计划恢复

在原 `ProspectiveCallLedger` 增加显式 `pause_for_review`、`resume_review`、`continue_review`；只允许从已经保存的waiting_review恢复，核对快照、全部产物、响应绑定及用量。未知预约、停止批次、非检查点中断和耗尽预算不恢复。消费检查点用进程文件锁保护，第二次接续失败；不重新执行已发送模型调用。

在原 `UnifiedResearchWorkflow` 增加JSON待审状态导出/恢复，包含组合任务内部确认状态，并核对数据指纹、规划模型配置、工作流选项和对话版本。账本负责外部文件哈希绑定；方法本身不将任意外部JSON当可信输入。

七项新增测试通过，其中注册贸易工作流经历保存→重建对象→恢复→confirm后生成可验证交付，规划模型仅调用一次；其余覆盖配置变化、响应损坏、未知预约及重复接续。测试使用离线模型，没有新GLM调用或语义成绩。

仍未完成：四场景运行器还未使用这些新接口自动接续；gap、政策主/B、最终报告审查全部节点的恢复整链测试尚未完成。live入口继续禁用。账本级resume_supported不代表项目级工作流已能自动恢复；下一阶段Astra中完成运行器阶段接线及整链测试，不再添加另一套恢复框架。

### 后续实现进度：宿主审核存储组件

已新增 `src/tradeintel_ai/host_review.py`：原始审核材料与显式提交分别保存，绑定批次快照、问题/阶段、完整材料指纹和审核身份；没有提交就返回待审异常，不生成任何事实标签。使用完整临时文件写入、fsync和不覆盖发布，同一提交可重复读取，但不同提交不能覆盖已有判断。重新打开存储后重新检查材料与判断的绑定，并调用现有审核校验器重新核验。

已验证10项新测试；与现有live入口的11项共21项定向测试通过。覆盖重开后继续提交、冲突/过期提交、损坏材料、未完成临时文件、拒绝结果不变为通过，以及无引用但正确的B回答可由显式判断判对、否定句可判错。测试中的判断由测试数据明确给出，不是新的自动裁判或真实模型成绩。

边界：本组件只恢复审核文档，不恢复运行器的执行位置。`workflow_resume_supported=false`。尚未接入gap审核、账本阶段恢复、工作流确认状态恢复或实际provider批次；live入口仍阻断。不得把此组件写成整批恢复完成。

下一步仍用Astra中：把运行器按准备/待审/确认交付/事实审核/对照/完成拆成可保存的阶段；显式保存并验证工作流待确认状态，接入本存储。检查点必须在进入下一次API调用前完成。已有预约但缺完整响应仍停止，不能重发。不用新框架替换原工作流，不重新索要用户授权。

继续复用原账本/运行器，实现显式阶段检查点和宿主审查提交，不再添加自动关键词裁判。Astra中负责这部分状态恢复与方法审查，规范锁定后批量实现/回归可用Luna最高。

1. 首次请求前持久化完整快照：题文、独立参考、代码/数据、实际生成配置。摘要必须对应磁盘内容；配置不符即停。
2. 每次模型请求先预约，收到响应后先保存响应和阶段产物，再生成带哈希审核包。状态为waiting_review；宿主读取包中的完整计划、gap、报告、每条主张与实际引文，提交理由和见证。缺失提交不执行后续请求。
3. 恢复时重新核对快照、产物、审核提交的绑定和阶段状态。已完成调用只读取保存响应；预约但无完整响应视为不确定，停止且不重发。禁止靠重新运行整批重建进度。

恢复测试必须覆盖：正常等待/提交/继续、不重复发送、未知预约、损坏响应、过期审核、配置变化、进程在写入中断、四场景完整离线演练。全部通过后由宿主审核实际预检文件，再在现有用户授权内开展有界真实开发批次。
