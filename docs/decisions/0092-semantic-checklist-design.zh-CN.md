# 0092：把原文分段与回答完整性分开验收

## 审查结论

0091按冻结规则拒绝第一题是历史事实，不改写为通过。但“两个独立问题一定要输出成两个原文片段”并不是最终业务价值。核心要求应当是：问题范围没有被改动，每个必答点都得到正确、有证据的回答，或明确说明不能回答。

代码复核发现，`request_coverage.TASK_IDS`把所有policy片段映射到同一个policy_question；`UnifiedResearchWorkflow._obligations`也只建立一个政策任务。即使模型已经拆成两段，`request_results`仍从这个共享任务复制执行状态。生成草稿后两项都会显示needs_review，不能分别说明生效日已支持、税率漏答。

这不是代码把漏答谎报为语义完成：它一直保留semantic_coverage_verified=false。真正的缺口是缺少独立、可记录的逐必答点审查。继续优化分段格式而不补这个环节，不能解决回答完整性。

## 离线证据

新增5项刻画测试`tests/test_requirement_granularity_audit_0092.py`：

1. 两个政策片段有不同request ID，但共享同一个执行任务。
2. 模拟“只回答一问”和“回答两问”，现有逐项执行状态完全相同，均待审查。
3. 合并/拆开原文都能通过现有字面和映射校验，政策问题内容相同。
4. 含逗号的单问、无标点的并问、否定限制、引述背景说明不能按标点数认定问题数。
5. 把另一个问题错误标成背景，也可能通过字面检查；审查必须从用户原问题出发，不能只看模型登记的ID。

第4/5项是人工构造分类的边界示例，绝不是模型分类测试。5项新增+相关回归合计26项通过，0.554秒；无网络、无训练，未运行全套。没有改变运行器、模型提示或旧结果。

## 已确定的后续实现规范

保留现有执行引擎和原文覆盖机制，不增加模型调用，不新增智能体。只在新的开发运行协议里把一个approve替换为可追踪的逐项审查记录。

### 1. 两层职责

- request_units用于原文位置、范围、路由核对。原文不遗漏、不改写、任务类型正确仍是硬门槛。相同政策任务中完整保留多问的合并片段，本身不再自动判业务失败。
- 独立review checklist用于答案完整性与事实支持。开发题的清单由审查者根据原始问题在首次调用前写定，不从模型片段数量推导。清单不发送给模型，参考答案也不发送。

这是一项明确的协议变更，不适用于0091原批次追溯改分。新版本的提示允许同任务片段合并，仍禁止把独立请求藏进背景、漏原文或忽略不支持范围。旧数字偏移兼容模式和历史实验不追改。

### 2. 清单和审查记录的最小字段

清单每行含宿主分配的id、原问题quote、required_answer（要回答什么，不是预置答案）、task、expected_disposition。允许两项必答点引用同一个完整原句，不强求互不重叠；必答点不是字符分段。

每次计划审查保存清单哈希、原问题/计划哈希、审查者、逐项covered/omitted/wrong_scope/needs_clarification及简短理由。covered只说明请求被完整传入正确任务，不意味着已答对。任何omitted/wrong_scope即停；不支持的份额必须明确拒绝或具体澄清整题，不能执行子集。

每次答案审查保存交付哈希、清单哈希、审查者、逐项supported/missing/contradicted/unverifiable及理由。政策supported需记录实际回答中的claim位置/原文和对应evidence引用位置、短证据摘录；贸易supported需记录本地确定性结果字段与冻结参考核对结果。回答、证据文件或清单改变后审查不能继续算有效。

宿主检查记录完整、ID无重复遗漏、哈希一致、引用确实存在；审查者负责理解摘录是否支持主张。程序不得把有摘录等同事实成立，结果应称reviewer_supported，不把底层semantic_coverage_verified改成true。空理由、缺必答行或不存在的引用不得批准。

合并需求但完整答两问可以通过；即使拆成两行，漏答一问也必须失败。答案额外的无支持主张、错误因果结论仍须作为整体检查失败，不能只检查清单内的句子。

### 3. 交互与范围

保留现有受控终端逐步查看方式，助手可以读输出、检查文件后逐项提交审查，不假装用户手动确认。计划核对之后才查金额/生成回答，回答核对之后才进入下一题。不增加另一套跨轮恢复系统，不自动approve。普通产品问题的清单仍须由审查者另行核对，4题开发清单不是通用自然语言语义识别器。

新增单独版本的清单与新批次清单指纹；旧0090/0091产物不覆盖。保留最多6次调用、已报告30000tokens后停止、首错停止、未知用量、调用前记账与禁止续跑等约束。

## 后续试验的假设、基准、门槛与停止条件

- 假设：把格式分段降为呈现信息、用独立必答点逐项审查，可以避免合并格式造成的误拒，同时不放过真正漏答。不是声称能提高GLM本身能力。
- 基准：0090冻结实现与0091原始返回，保持历史失败。离线对照至少包括合并+完整答、拆分+漏答、错误方向、无效引用、否定/引述、单问、不支持份额、清单或文件被改动。
- 防泄漏：运行代码不硬编码题号/两项数量/税率/日期/金额，不按标点硬拆。开发清单及参考只给审查者，不进入规划或回答消息。既有4题都是已见公开开发题，不能当盲测或计算总体准确率。
- 实现采纳门槛：上述正反例都按语义审查记录正确放行/拒绝；旧预算、安全和交付测试通过；审查记录完整可追溯；不新增API需求。
- 真实试运行：实现和离线审查通过后，单独冻结新协议与输出目录，仍用0089四题、glm-4.7/0/60、1536/768、最多4规划+2回答；不得直接重启旧批次。完整通过要求所有必答点和整体边界均由审查者核验，而非要求特定片段数。
- 停止条件：实现需要改研究口径、自动认定语义或扩大调用量时暂停交给Astra中判断。真实首错停止，不换模型刷分。局部事实支持不代表整题通过，未运行题保留。
