# 决策 0007：先采用供应商无关的 OpenAI-compatible 模型适配器

- 状态：已实现离线适配器与契约测试；真实 provider 尚未选择和评估
- 日期：2026-09-02
- 适用阶段：Phase 10c

## 背景

TradeShock AI 已有六个只读工具、结构化证据包、60 道本地契约评估和因果安全后卫。六个工具中，五个是模型可请求的查询工具，`build_evidence_bundle` 由程序依据真实成功结果内部生成。下一步需要接入真实大语言模型，但当前环境没有模型 API key，也没有理由为了“看起来像 AI”立即引入大型框架。

## 候选方案

| 方案 | 优点 | 当前风险 |
| --- | --- | --- |
| 直接绑定某家 SDK | 文档和高级功能较完整 | 供应商锁定；依赖和格式进入核心逻辑 |
| 本地大模型 | 不必把问题发给远程服务 | 安装、显存、模型质量和工具调用兼容性不确定 |
| 薄的 OpenAI-compatible HTTP 适配器 | 依赖少，可切换远程或本地兼容服务，边界清楚 | 仍需在真正 provider 上做冒烟和质量评估 |

## 选择

先采用第三种。`OpenAICompatibleModel` 只实现：

1. 从环境变量读取 endpoint、模型名、可选 API key、超时和温度；
2. 把内部消息和五个模型查询工具 schema 转成 `/chat/completions` 请求；
3. 把文本和结构化 tool calls 转回 `ModelResponse`；
4. 对 HTTP、连接、JSON 和工具参数错误做不泄漏秘密的失败处理。

它不负责数据库查询、计算、证据打包、评估答案或放宽因果门槛。

## 方法边界与验收

- **假设**：如果模型服务能返回合法的工具调用格式，现有工具循环可以在不改数据和因果规则的情况下复用它。
- **对照基准**：确定性路由基线 + 离线 `MockModel`。
- **防泄漏规则**：只发送用户问题、系统约束、已登记工具 schema 和工具返回结果；不发送隐藏答案、API key、任意 SQL 或未登记的网络地址。
- **采纳门槛**：离线适配器测试通过；原有 65 个测试全部通过；至少一次真实调用符合响应契约；真实模型评估中不支持的因果断言为 0。
- **停止条件**：若 provider 不支持结构化工具调用、产生未解析参数、或真实评估未达既定门槛，停止在适配器/工具层修复，不引入更多 Agent 或 RAG 组件。

## 为什么现在不声称“已经接入 AI”

适配器代码通过只能证明翻译层可运行，不能证明某个真实模型会正确选工具或理解限制。只有配置明确的 provider、保存可复现的模型信息并重跑 60 道评估，才能报告真实模型表现。没有 key 时保留 Mock 是诚实的离线开发状态，不是失败。
