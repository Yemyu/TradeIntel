# 0086：预算、配置快照与交付状态

> 历史实现记录。0087复审发现并修复旧目录污染、终态先于最终报告和脱敏/中断缺口。当前权威交付核对与基础配置边界见[0087](0087-delivery-review-and-request-coverage.zh-CN.md)，本页不证明完整验收已通过。

本阶段解决的是“这次运行到底做了什么、是否超出边界、文件是否真的交付”这一类工程可审计问题，不是增加新的经济结论，也不是重新尝试已经阻断的因果匹配。

## 决定

统一入口使用宿主固定的两段模型预算：规划最多 1 次，政策回答最多 1 次，总计最多 2 次。生成层已有单次边界；本阶段把同一限制写入预览、规划审计、模型调用账本和最终结果。自动重试仍关闭。

每一段调用保存无密钥配置快照：来源类型（fixture/live/no_model）、适配器类型、请求模型名、端点的主机和路径、超时、温度以及“没有记录 API key”的明确标记。端点的查询参数、用户名和密码不写入快照。

确认后先在交付目录旁保存 `*.delivery-intent.json`，再创建运行目录。正常运行新增 `delivery-status.json`；它列出应有文件、已出现文件、缺失文件、执行状态、预算、配置和是否中断。业务状态与文件交付状态分开：例如业务结果可以是 `partial`，只要审计、结果和报告文件都存在，交付状态仍可为 `complete`。

如果在执行或最终写文件时发生超时、键盘中断或其他异常，系统不自动重试，并尽力写入 `delivery-status.json` 和旁路 intent 文件，记录 `failed` 或 `interrupted` 及缺失文件。确认令牌已经消耗，不能用同一令牌恢复；当前只提供人工检查线索，不宣称支持自动续跑。

## 验收边界

- 必须能从最终目录看到预算和配置快照，且搜索不到 API key。
- 正常 fixture 运行必须出现完整交付标记，缺失文件为空。
- 中断必须留下中断状态和缺失文件列表，而不是静默地看起来像成功。
- 预算越界只记录为失败/违规，不为了得到好看的结果自动再调用。
- 这一阶段没有在线 API、没有训练或微调、没有改变因果状态。

## 结果

新增 `tests/test_delivery_status_0086.py` 覆盖正常交付、fixture 政策回答和中断路径。完整回归测试在阶段结束时记录于项目计划和总参考文件。
