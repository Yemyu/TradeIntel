# TradeIntel 使用说明（本地中文版）

这份说明面向第一次运行项目的人。TradeIntel 是一个本地贸易政策研究助手：程序保存官方政策原文、登记政策覆盖的 HTS8 商品和版本化贸易数据；确定性代码计算金额与占比；可选 AI 只能围绕给定证据整理解释，不能代替人确认政策事实。2026-09-28 曾对一份已参与开发的公告做过一次 DeepSeek API 诊断和一次 GPT-6 Luna Max 聊天诊断；这不是日常使用时自动调用模型的证明，具体结果见[模型评测](MODEL_SELECTION.zh-CN.md)。

## 1. 启动本地页面

在项目根目录执行：

```bash
cd /Users/ye/dev/projects/TradeIntel
PYTHONPATH=src:. .venv/bin/python scripts/run_web.py --host 127.0.0.1 --port 8899
```

如果入口参数因本地版本不同而变化，可以直接运行项目已有的服务脚本，再在浏览器打开：

- `http://127.0.0.1:8899/`：主看板，查看登记政策、版本和确定性贸易查询。
- `http://127.0.0.1:8899/session-research`：研究会话；先确认月份/商品范围，再生成证据和 A3 程序稿。
- `http://127.0.0.1:8899/update-check`：检查本地数据版本。未登记真实抓取源时只记录检查时间，不会假装联网更新。
- `http://127.0.0.1:8899/announcement-import`：新官方公告的候选导入路径。

启动前不需要把 API 密钥写进前端；浏览器永远不应看到密钥。上述 R2 API 调用是隔离的开发试验，不等于用户在页面中已配置好并可稳定调用模型；离线测试不会消耗 API 次数。

## 2.1 当前收口后的完整报告链

研究会话生成的第一版是程序确定性 A3：政策版本、商品范围、金额、分母、来源和局限都由代码写入。生成后，开发或未来的模型适配器可以准备“证据关联解释”输入；它会把同一事实目录、A3 和严格 JSON 合同绑定成一个不可变快照。

当前产品流程不会自动替用户调用模型。开发者可用“解释输入”返回的 `messages` 做聊天模拟，再把原始 JSON 通过解释提交接口送回同一解析器；也做过隔离的模型 API 开发诊断。两者都不等于页面已提供稳定、免配置的模型服务，也不代表最终产品要求用户手工复制粘贴。

解释必须先通过结构校验，再逐条人工确认。未通过、缺证或修改了政策/数据版本时，不能把模型文字并入报告，也不能导出 AI 报告。审阅通过后，导出文件由“程序 A3 + 已接受的 AI 解释 + 审阅记录”组成；原始回答、摘要和版本绑定会保留在本地审计目录。

当前新增的本地接口（供开发集成测试使用）是：

```text
POST /api/session/task/explanation/prepare
POST /api/session/task/explanation/submit
POST /api/session/task/explanation/review
```

确定性程序草稿在报告生成后即可读取或下载：

```text
GET /api/session/draft?session_id=...&task_id=...
```

它只返回 A3 程序稿，不包含未经逐项审阅的 AI 文字。最终 `/api/session/export` 仍需要任务进入 `exportable`，并重新核对报告摘要、数据版本和事实目录摘要。重复审阅不会覆盖旧决定，会追加保存审阅版本历史。

它们都要求已有确定性报告和同一 `session_id`/`task_id`。`submit` 的 `channel` 会明确记录为 `chat_simulation`、`stub` 或 `api`；接口本身不会因为填写 `api` 就自动创建网络请求。

## 2. 查询现有登记案例

主看板的“查询数据”只读取已经发布的数据版本，并重新计算：

1. 全部来源消费进口额；
2. 中国原产金额；
3. 中国金额占全部来源金额的占比；
4. 选择月份和 HTS8 后的分商品明细。

这些数字是所选商品编码在对应月份的贸易观察，不表示每笔进口都满足政策条件，也不是损失额或政策造成的变化。页面显示的公告链接和数据版本用于追溯；数据版本发生变化时，旧研究仍指向原版本。

新公告还可以按四种关系分流：完整编码相符、上层商品背景、中国大陆贸易背景、只整理公告原文。后三种会清楚写出统计商品范围与政策对象的差别；凡是包含公告未覆盖商品的金额都只能作为背景，不能称为政策覆盖额。参见[当前可交付范围](handoff/DELIVERY_SCOPE_20260927.zh-CN.md)。

## 3. 新公告导入与统计范围确认

新公告不会直接覆盖旧政策，也不会因为导入就进入检索。用户需要提供官方 URL 与完整公告正文；当前流程不会自动上网搜索、抓取或更新政策。页面按以下顺序工作：

### 第一步：登记原文

填写政策 ID、来源 ID、官方 URL，粘贴完整公告正文，点击“登记为候选”。成功后会得到 `doc_version`，文档状态是 `disabled`。登记是保存原文，不是采纳政策。

等价的本地接口是：

```text
POST /api/announcements/import
```

### 第二步：生成确认模板

点击“生成确认模板”。系统提供 13 个字段：标题、发布日期、生效日期、24 小时时钟、时区、入境事件、原产地、HTS 税号、税率、税率含义、适用条件、例外、修订引用。

每个字段必须选择一种诚实状态：

- `known`：填写值，并粘贴保存原文中的逐字引文和 `section_id`；
- `unknown`：不猜值，必须写明为什么目前不知道；
- `conflict`：至少保留两条相互冲突的证据，留给人工解决。

“quote 匹配”只证明这段字确实存在于已保存公告，不等于语义审阅通过。

### 第三步：提交候选并启用

点击“提交候选校验”只做格式、字段完整性、引文位置和文档摘要校验，文档仍是 `disabled`。点击“确认并启用”后，服务器再次从磁盘读取并复核摘要；通过后才会把这一个精确 `doc_version` 变为 `enabled`。

启用结果一定包含：

- `rebind_required: true`：过去已经确认的研究范围绑定的是旧政策集合，必须重新确认；
- `coverage.trade_coverage: not_checked`：在没有受信任贸易查询产物前，绝不把任何金额称为精确政策敞口。

### 第四步：确认政策对象和要看的统计范围

页面会并列说明“公告限定的对象”和“统计表实际会计算的商品”，由使用者确认关联路线：

- **编码相符**：公告有完整 HTS8 时，沿用原严格商品报告。
- **上层商品背景**：公告只涉及某个商品组的一部分时，可看父级商品的整体进口背景；报告会说明其中有公告未覆盖的商品。
- **中国大陆贸易背景**：公告适用于广泛中国货品且未知例外不决定统计对象时，可以查看数据包里中国大陆来源的整体进口背景；不把香港并入，也不称作政策金额。
- **只整理公告原文**：若邮寄方式、包裹价值、企业资格、审批用途等关键条件无法从月度商品表识别，就只出原文事实卡，不画贸易图、不补一个全国金额。

每次确认都绑定公告版本、逐字引文及数据版本。公告或确认内容发生变化时，需要重新确认。每条路线都不会把观测金额解释成实际征税金额、政策影响或因果效果。

商品背景路线只接受已发布月份；国家背景的原始 ZIP 复算目前只验证了 `2025-02` 与 `2026-07` 两个月。不能把这两个月的核验扩大成全部月份均已通过。

## 4. 确定性解析器做什么

`src/tradeintel_ai/announcement_parser.py` 是离线确定性解析器，不调用模型。它对 CBP 公告正文做三类安全工作：

- 从明确的 `take effect on` 句抽取生效日期；
- 从 `additional N percent rate of duty` 句和商品行抽取税率与 HTS8；
- 为每个 known 字段保存原文逐字引文；无法抽取的字段保留 `unknown` 和理由。

当前真实本地材料的验收结果是：2025-01-01、50%（28046100/38180000）、25%（81019400/81019910/81019980）均可抽出。`9903.91.05` 和 `9903.91.11` 是 Chapter 99 的申报标题，不会被误当作商品 HTS8。

对官方 GovInfo FR2025-23912 的首次自动解析为 13/13 `unknown`，因为它使用连续八位税号和不同句式；后续 R2 迁移使用人工逐字段确认完成产品链路，不把人工确认冒充解析器准确率。

解析器只是候选生成器，不拥有启用权限；解析结果仍必须经过上面的 K3 人工确认流程。

## 5. 会话研究流程

`/session-research` 的顺序是：新建会话 → 提出问题 → 确认月份和商品 → 读取确定性证据 → 生成 A3 程序稿 → 人工审阅 → 导出。确认前不会执行查询；刷新页面会从本地会话恢复。

A3 程序稿列出观察值、税率与条件、来源和限制。它不是模型自由回答，也不是因果结论。未来 AI 解释若获准运行，也必须绑定同一数据版本和证据目录，并经过逐项审阅。

## 6. 更新与失败边界

- 没有真实抓取源：更新检查只记录时间，状态为 `no_fetch_source`。
- 没有变化：不创建新数据版本。
- 候选版本需要审阅：只暂存，不激活。
- 激活失败：旧活动版本继续可用，失败写入审计记录。
- 任务已开始但没有原答：状态为 `unknown_outcome`，不会自动重试或重复收费；只有人工明确决定后才能重试。
- 任何公告正文、字段或版本摘要发生变化：原确认失效，必须重新确认。

## 7. 当前项目边界

四种公告—数据路线、人工范围确认和本地报告页面已实现；它们本身不调用模型。两份新公告的产品回放为 0 次模型 API，不能当 AI 成绩。另有 R2 已见公告的两份开发回答：DeepSeek API 为 7/7 覆盖但因一条无据断言未通过；GPT-6 Luna Max 聊天诊断为 7/7 覆盖且未发现无据额外说法。渠道与会话上下文未隔离，不能公平比较模型，也不能外推准确率；人工是否省时仍未测。产品仍是单用户本地原型，不应描述成已部署的实时服务；自动政策发现和每日抓取也未完成。完整证据边界见[当前可交付范围](handoff/DELIVERY_SCOPE_20260927.zh-CN.md)。

## 8. 常见问题

**为什么导入后搜不到公告？**

因为导入后的状态是 `disabled`，这是安全设计。完成 13 字段确认、逐字引文复核和人工启用后，才允许进入后续受控流程。

**为什么覆盖不是 exact？**

因为 `not_checked` 代表还没有绑定月份、数据版本和受信任贸易查询。它比编造一个“精确金额”更诚实。

**为什么解析器不把所有空字段补齐？**

因为没有原文证据就不能猜。unknown 会把缺口留给人工确认，避免把模型或正则的猜测写成政策事实。
