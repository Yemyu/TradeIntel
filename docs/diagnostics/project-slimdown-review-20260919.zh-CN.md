# TradeShock AI 项目瘦身审计（2026-09-19）

## 结论先行

WorkBuddy 的 K1—K5 交付在“按既定方案实现离线边界和测试”这个范围内合格；它还不能被称为“AI 产品已完成”。本轮没有删除文件，也没有调用真实模型。

证据：K1/K2/J1—J4/K3/K4 定向 Python 测试 57 项通过，页面 fixture 3 项通过；全量测试为 1096 项，其中 3 项既有失败、44 项历史冻结哈希守卫、4 项旧因果模块在当前环境发生 SciPy ABI 导入错误。真实 provider、R2 未参与开发的新公告、贸易覆盖重绑定和模型质量验收仍未完成。

## WorkBuddy 交付的质量边界

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 证据、版本、候选确认、审阅导出边界 | 合格 | 有绑定版本、逐字引文、哈希、状态机和拒绝门 |
| 会话、重复任务、失败恢复 | 合格（离线） | stub/fixture 已测；未证明线上并发和真实 provider |
| 新公告导入第一段 | 部分合格 | 可以登记为 disabled 候选并逐字段确认；还没有完成新公告的真实贸易覆盖和报告重绑定 |
| 公告解析器 | 有限合格 | 只在保存的 CBP 样例上通过；是确定性正则解析，不是通用法律解析器 |
| AI 生成质量 | 尚未验收 | 真实调用被双门禁阻止；离线 stub 不是模型准确率 |
| 整体产品 | 未完成 | 仍是本地单用户原型，数据截止已有快照，不能自动获取最新贸易数据 |

所以，问题不是 WorkBuddy “完全做坏了”，而是它严格执行了离线施工任务；原任务本身没有包含真实模型质量、R2 迁移和生产部署。

## 为什么显得过大

当前检出目录约有 99 个 Python 源文件、139 个脚本、206 个测试、490 个文档文件。它把三类东西放在同一个根目录：

1. 当前产品主链：政策候选/版本 → 证据与贸易查询 → 报告 → 审阅/导出 → 受控更新。
2. 历史研究与失败实验：因果匹配、G2、旧 planner/intent 版本和大量回放脚本。
3. 验收与交接档案：冻结哈希、运行包、课程参考和临时产物。

这不是“功能越多越强”，而是产品代码、实验档案和学习材料尚未分层。

## 建议的最小主产品（先保留）

主产品只保留一个可演示纵向切片：

1. 本地网页：主入口、会话研究、更新检查、新公告导入、审阅导出。
2. 政策与来源：`policy_documents`、`policy_candidates`、`policy_search`、`announcement_flow`、`announcement_parser`、`source_registry`。
3. 证据与报告：`brief_fact_catalog`、`brief_business_view`、`evidence_linked_brief`、`response_contract`、`provider_executor`。
4. 数据与版本：`policy_exposure_tools`、`exposure_version_store`、`controlled_update`、`repository` 及现有 MySQL/本地数据快照。
5. 会话与审阅：`session_store`、`session_brief`、现有审阅存储和导出门。
6. 最小运行说明、当前状态和一份可复现演示数据。

“因果识别”在主产品中只保留安全拒答/历史说明，不再作为功能目标；相关历史数据暂时只读保存，避免误删导致现有安全门和旧报告不可解释。

## 只适合归档、暂不进入主路径的内容

以下内容可以在确认依赖后移到 `archive/` 或单独的历史分支，但本轮不直接删除：

- 因果匹配、pre-policy trajectory、control eligibility 等历史实验脚本和报告；
- G2/G2 revision 的准备包、旧账本和冻结输入；
- 已被后续版本替代的 planner/intent 回放脚本与旧试验输出；
- 课程参考源码、课程适配检查和只读 vendor 资料；
- `tmp/` 下除最新验收证据之外的中间运行包。

归档前必须通过三项检查：主网页和 CLI 不再导入；当前验收测试不再依赖；历史报告仍能由明确路径读取。不能按文件名直接删，因为现有 `tools.py`、`repository.py` 仍用因果状态做安全拒答和数据目录校验。

## 目前不应删除的内容

- `data/raw/` 中保留的官方压缩包和来源清单；它们是重新生成贸易快照的依据。
- `data/processed/` 的当前政策暴露快照、来源哈希和 MySQL 导入所需表。
- `.local/` 中的状态/账本（不要提交到 Git，也不要用删除代替重置）。
- `docs/handoff/`、`PROJECT_CONTEXT_REFERENCE.zh-CN.md` 和当前运行日志；它们记录了为什么没有调用真实模型及哪些结果不能宣传。

## 是否需要 Sprite 重做

当前证据不足以判定“需要推倒重做”。更合理的顺序是：

1. 让 Astra 或 Sprite 只审查本文件的“最小主产品”和“归档清单”，不重写全部代码；
2. 冻结保留/归档边界以及 R2、真实模型验收标准；
3. 再由 Luna/WorkBuddy 做可逆归档和依赖回归；
4. 最后才决定是否放行一次有限真实模型调用。

如果 Sprite 给出的方案无法明确保留政策版本、证据引用、审阅门和失败恢复，就不应采纳，即使它的页面看起来更完整。
