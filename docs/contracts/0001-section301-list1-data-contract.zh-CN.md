# 数据契约 0001：Section 301 List 1（中文版）

> 这是给项目学习使用的中文版本。英文原文保留给以后 GitHub 展示和申请材料使用。  
> “数据契约”不是某种编程语法，而是团队在写代码前约定：**数据从哪里来、每个字段是什么意思、什么情况算错误、怎样才算完成。**

- 状态：实现前草案
- 日期：2026-08-28
- 相关决策：[`0001-initial-policy-case.zh-CN.md`](../decisions/0001-initial-policy-case.zh-CN.md)

## 1. 目标

建立一套可追溯的月度数据，把官方 Section 301 List 1 的政策范围，与美国按商品和原产国划分的进口数据连接起来。

第一版数据必须支持下面的问题，而且不能依赖大语言模型自己计算：

> 2018 年 7 月 6 日以后，List 1 商品从中国进口的金额和份额怎样变化？哪些其他供应国的份额增加了？

简单理解：政策文件告诉我们“哪些商品受到政策影响、什么时候生效”；贸易文件告诉我们“每个月实际从哪些国家进口了多少”；数据契约保证两者连接时不会偷偷改变口径。

## 2. 输入数据

### 2.1 政策输入

- 来源：美国贸易代表办公室（USTR）/《联邦公报》2018 年 6 月 20 日的措施公告
- 官方 PDF：`https://ustr.gov/sites/default/files/2018-13248.pdf`
- 需要读取的内容：Annex A，也就是列出 818 个 HTSUS 商品税号的附件
- 政策针对的原产国：中国
- 额外关税税率：25%
- 生效日期：2018-07-06
- 适用环节：进入消费，或从保税仓库提取并进入消费

### 2.2 贸易输入

- 来源：美国 Census 国际贸易数据
- 数据集：按 HS 商品编码和原产国划分的美国月度进口数据
- 时间范围：2016 年 1 月至 2019 年 12 月
- 首选详细程度：HTS 10 位
- 金额口径：进入消费的月度进口金额
- 覆盖范围：受影响商品的所有原产国；网页展示时可以只显示主要供应国

第一版优先使用官方公开批量文件，这样不需要用户提供邮箱或 API 密钥。以后可以把 Census API 加入增量更新流程，但那是工程增强，不是当前第一步。

## 3. 必须生成的结果

### 3.1 `policy_events`：政策事件表

| 字段 | 含义 |
|---|---|
| `policy_id` | 稳定的政策编号，例如 `us_301_list1_2018` |
| `policy_name` | 人能看懂的政策名称 |
| `importer` | 进口国：美国 |
| `target_origin` | 被针对的原产国：中国 |
| `announcement_date` | 公告日期：2018-06-15 |
| `effective_date` | 生效日期：2018-07-06 |
| `additional_rate` | 额外税率：0.25 |
| `source_url` | 官方来源链接 |

这张表回答：“是什么政策、对谁、何时生效？”

### 3.2 `policy_products`：政策商品表

| 字段 | 含义 |
|---|---|
| `policy_id` | 连接到政策事件表 |
| `raw_hts` | 初始 Annex A 中原样打印的税号 |
| `canonical_hts8` | 审核后用于匹配的 8 位标准税号 |
| `source_annex` | 来源附件：Annex A |
| `source_page` | 税号所在的 PDF 页码 |
| `amended` | 后续官方通知是否修正过 |
| `amendment_source_url` | 有修正时的官方来源 |
| `exclusion_status` | 商品排除事项状态；初版为 `not_yet_modelled` |

这里同时保存 `raw_hts` 和 `canonical_hts8`，是为了避免把官方原文和我们的匹配版本混为一谈。

### 3.3 `trade_import_monthly`：月度贸易表

| 字段 | 含义 |
|---|---|
| `year` / `month` | 观察年份和月份 |
| `origin_code` / `origin_name` | 供应国代码和名称 |
| `hts10` | 美国进口记录中的 10 位详细商品编码 |
| `hts8` | 从 10 位编码取得的前 8 位，用于连接政策清单 |
| `import_value_consumption_usd` | 进入消费的月度进口金额（美元） |
| `quantity_1` / `quantity_unit_1` | 第一数量指标及其单位（有数据时） |
| `source_last_update` | 数据来源提供的最后更新时间 |
| `source_file` | 对应的原始下载文件 |

### 3.4 `analysis_panel`：分析面板

这是把政策表和贸易表连接后的分析用数据表。它至少需要包含：

| 字段类别 | 含义 |
|---|---|
| 商品、国家和月份字段 | 每一行对应什么商品、哪个供应国、哪个月份 |
| `listed_in_list1` | 商品是否出现在 List 1 清单中 |
| `target_origin` | 这一行是否来自中国 |
| `post_effective_month` | 是否属于 2018 年 7 月及以后 |
| `scheduled_treatment` | “List 1 商品 × 中国 × 生效后”的计划处理标记 |
| `exclusion_modelled` | 是否已经纳入商品排除事项 |
| 金额、份额和数量字段 | 后续分析需要的结果 |

注意：在商品排除事项还没有纳入前，`scheduled_treatment` 只能表示“按计划属于受影响范围”，不能被写成最终实际税负暴露。

## 4. 必须遵守的规则

1. 商品税号必须作为文本保存，避免前导零消失。
2. `raw_hts` 必须保留官方打印形式，官方修正要放在单独的标准字段里。
3. 初始 Annex A 中的 `9033.00` 必须根据 2018 年 8 月 16 日官方修正改为 `9033.00.90`；不能自行补零或猜测。
4. 对合法的 10 位进口编码，使用前 8 位生成 `hts8`。
5. 金额必须是美元数值，负数要拒绝。
6. 原始文件保持不变，并记录下载日期和校验值（checksum）。
7. 不能悄悄删除格式错误的政策税号、未知国家、缺失值或重复记录。
8. 不同版本的来源文件要能够区分，不能把修订版当成从未变化过的数据。
9. 普通进口金额和进入消费进口金额不能混在同一个字段名下。
10. 一个商品只有在检查过后续关税清单后，才能被称作干净的对照组。
11. 在排除事项、提前进口、比较组和政策前趋势都没有检查前，不能作因果结论。

## 5. 出错时应该怎样处理

- 如果 Annex A 提取结果不是 818 个唯一税号（排除实施标题 `9903.88.01` 后），就停止并生成提取审计报告。
- 如果唯一的非 8 位条目不是 `9033.00`，或者官方修正没有明确把它替换为 `9033.00.90`，就停止，不能自行猜测。
- 如果税号长度不对或包含非数字字符，要在错误报告中保留原文，并排除出连接操作。
- 如果某个月的来源文件缺失，要把该月份标记为不完整，不能当作贸易额为零。
- 如果金额无法转换为数值，要报告具体来源文件和行标识。
- 如果按预期汇总后仍然出现重复的“商品—国家—月份”记录，就停止生成分析面板并报告重复维度。
- 如果不同年份的商品分类发生变化，必须单独作出并记录对应关系决定。

## 6. 验收标准：怎样才算完成

第一版只有同时满足以下条件才算通过：

1. 初始 Annex A 产生 818 个唯一清单项：817 个 8 位条目，以及已记录的 `9033.00` 异常项。
2. 官方修正得到验证，并把 `9033.00` 替换为 `9033.00.90`，形成 818 个唯一的 8 位标准税号。
3. 政策税率和生效日期与官方公告一致。
4. 2016 年 1 月至 2019 年 12 月的全部 48 个月都有记录，或者被明确标记为缺失。
5. 金额是数值且不为负数。
6. 每条处理后的记录都能追溯到具体原始文件和下载记录。
7. 在声明的汇总层级上，“商品—国家—月份”键唯一。
8. 至少一个独立的总量能够与官方来源对账，并记录允许的误差范围。
9. 自动化测试覆盖政策税号解析、日期边界、税号匹配、重复记录和缺失月份。
10. 数据质量报告能够区分零贸易、数据缺失、无效数据和被抑制的数据。
11. Git 或生成结果中不能出现密钥等秘密信息。

## 7. AI 的实现顺序

AI 可以负责重复性的实现，但必须按小步骤生成可检查的结果：

1. 下载并记录官方政策公告的指纹。
2. 提取 Annex A 税号并生成审计报告。
3. 获取并盘点官方月度进口文件。
4. 不修改原始文件，解析其中的字段。
5. 检查结构、类型、税号、月份覆盖范围和重复记录。
6. 建立政策清单与进口数据的匹配关系。
7. 生成分析面板和数据质量报告。
8. 在把整理后的表加载到 MySQL 前，先运行自动化验收检查。
