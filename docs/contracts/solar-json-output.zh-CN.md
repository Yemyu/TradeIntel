# 第二案例：先约束回答格式，不再逐次迁就回答

日期：2026-09-14。状态：离线实现，尚未真实验证，不采纳到网页默认模型。

## 为什么改

上一次恢复已收到两个商品的说明，但模型使用了约定外的状态、额外字段和税号格式，程序无法安全接收。继续看到一种答案就加一个兼容分支，会使接口越来越不可预测。

本次不改政策答案、数据或成功门槛，改为在请求时明确使用 JSON 模式，并给第二案例的综合报告附一份机器可读的字段说明。可以理解为：先发空白表格和填写规则，而不是收到任意文章后再猜它想填哪一栏。

## 三层限制不能混为一谈

1. **JSON 模式**：要求输出可解析的 JSON 对象。
2. **字段契约**：指定税号、五项条件、supported/unknown、引用编号，以及禁止额外字段。提示中的 Schema 是填写说明，不是服务端强制执行。
3. **事实正确**：例如“额外税率”不能写成“总税率”，“其他税费如适用”不能写成必然征收。前两项成立也不能保证这一项。

核查依据：[智谱官方对话补全接口](https://docs.bigmodel.cn/api-reference/模型-api/对话补全)。所查文档的 response_format 列出 text/json_object，没有据此确认 GLM-4.7 支持严格 json_schema 服务端约束。因此实现只发送 json_object，不发送未经确认的 strict/json_schema 参数，不宣传强制字段保证。

## 实现与边界

- JsonResearchModel 为显式选择；solar pilot 使用它，原网页默认模型暂不替换，避免未验证服务选项影响已启用案例。
- 第二案例 brief/series_brief 按实际所问税号生成 Schema，运行时保存 requested-output-schema.json；不注入参考答案或评估结论。
- 运行冻结记录保存实际 response_format、模型及生成设置。服务拒绝参数时失败退出，不悄悄退回旧模式。
- 宿主仍验证每个税号每个字段恰好一次、状态与引用对应关系。保留已冻结的两种无损表示，不接受新的 known 状态或多余 requested_code。
- 报告仍须人工审阅；不激活第二案例，不覆盖原失败，不重跑已锁定的恢复目录。

## 验证和后续

本轮59项聚焦离线测试通过，零真实API调用；不是模型成功率，也不是全仓验收。

下一阶段先锁定有限服务能力验证：用不含政策答案的合成字段任务，比较同模型旧模式与JSON模式，固定提示、参数、输入和各一次调用上限，不重试。假设仅是新模式能够被服务接受并遵守该任务字段要求；两边逐字段检查，失败即停止扩大运行，不能据单个任务推断准确率提升。通过后才设计一次完整业务验证，仍需政策语义审阅，不能直接开放第二案例。正式调用前另存具体输入、哈希与token上限。

## 学习参考

**我们在训练模型吗？** 没有。这是改应用如何向模型提要求、如何接收和核查结果，没有更新模型权重。

**格式对了就能用了？** 不一定。像一张填得整齐的表也可能填错税率；所以程序检查结构，原始证据支持人工核查，二者都要保留。
