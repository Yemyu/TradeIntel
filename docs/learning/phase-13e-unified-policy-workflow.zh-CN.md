# Phase13e：不再只让实验脚本能跑通

## 这一轮做了什么

之前不同步骤散在不同脚本：一个问GLM，一个去掉代码框，另一个核对引用。本轮把它们接到同一政策问答入口，避免实际使用时又遇到已经解决的接口问题。

现在的流程是：

问题 → 检索冻结的官方原文 → 一次受限GLM生成 → 检查是否正常结束 → 只规范化JSON外包装 → 检查主张和引用 → 中文草稿与来源链接。

这仍是**政策文档问答入口**，不是整个项目已经统一成最终产品。原有贸易分析、确认流程、因果边界仍保留，不偷偷切换它们的默认入口。

## 可以怎样体验

不需要密钥的旧真实回答演示：

```bash
.venv/bin/python scripts/run_policy_retrieval.py --replay-last
```

这会通过新入口重放之前GLM真正返回过的回答，不调用API。终端最后会给出新报告路径，位于`tmp/policy-retrieval/run-.../report.zh-CN.md`。每次生成新目录，旧记录不会被覆盖。

只检索原文，也不调用API：

```bash
.venv/bin/python scripts/run_policy_retrieval.py --question "第二批关税何时生效？" --as-of 2018-08-23
```

确实需要一次新GLM回答时才使用`--generate`。程序沿用GLM-4.7、关闭思考、512输出tokens与60秒超时；密钥从项目环境变量读取，或在交互终端隐藏输入。本阶段没有运行真实生成，后续正式验收另定调用范围，不建议自己反复刷已知题。

## 需要理解的问题：参考答案

### 1. 为什么保留两份回答？

`raw_response.json`保存原始文本，`normalized_response.json`保存去掉代码框后的文本。这样可以证明我们只修了包装，没有替模型改日期、税率或引用。

### 2. finish_reason是什么？

是服务端告诉我们“为什么停止输出”。例如stop表示正常结束，length表示达到长度限制。只看到一段能读懂的文字，不代表整个答案已经写完。新真实入口要求正常结束，否则不把它作为完整草稿交付。

旧归档当时没有保存这个信息，所以重放报告明确保留“结束原因未知”，不能事后编一个stop。

### 3. token用量有什么作用？

它帮助观察输入与输出成本。新入口只保存服务返回的基础用量；没有提供的字段保持缺失，不填零冒充没有消耗。此次重放没有真实调用，所以新增API请求数为0。

### 4. 为什么叫草稿，不直接叫最终答案？

程序能检查引用编号是否真实、JSON是否完整，但不能仅靠这些确定每句话都被原文支持。例如之前“上午12:01”需要更清楚表达为“凌晨00:01（美国东部夏令时）”。本轮报告另列审查备注，没有悄悄改掉模型原文。

### 5. 这是不是又在训练模型？

不是。没有更新模型参数，也没有新增API调用。这里做的是把应用管道和错误记录完善，让同一种输入可以稳定经过相同检查。
