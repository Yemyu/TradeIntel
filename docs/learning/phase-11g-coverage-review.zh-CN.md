# Phase 11g：把表示错误和任务错误分开处理

## 这次完成的改进

新增独立v3候选。第一层使用有限同义表，把有逐字段原文依据的“只读查询”“美元消费进口额”“中国”等转成接口值；不转换未知国家或删除操作。第二层增加一次模型覆盖复核，比较原问题与计划，仅接受/澄清/拒绝，不能重写计划。复核失败撤销确认，执行边界仍沿用原只读证据流程。

CLI增加显式`--plan-v3`，真实使用最多规划+复核两次模型调用，不替换默认或旧版本。此调用方式仍为候选，不是已经完成新题验收。

## 真实实验结果

固定上批v2六份规划响应，新增六次glm-4.7复核，消耗2,626 tokens。5/6符合完整开发参考；原四个成功项无退步，P02中文字段导致的错误拒绝解除。

P03原来把“比较进口变化”错换成readiness。复核返回reject/coverage并引用“比较政策后的进口变化”，错误计划被取消确认。但期望是明确澄清比较窗口与基准，实际只告知需要检查，所以仍失败。这是安全改善，不能算完整任务成功。

没有自动确认或金额查询。原始日志与离线重放一致，助手完成逐题复核。259项全套本地测试通过。新实验只验证同义转换与覆盖复核组件，不是六次全新“规划+复核”的端到端测试，不宣称独立评估或正式采纳；旧v2的4/6不修改。

## 学习问答

### 两次模型调用是不是两个独立专家？

不是。这里同一种模型用不同职责提示完成两次调用，可能犯相关错误。复核提供额外检查，不能等同独立人工审核，所以coverage_verified保持false。

### 为什么复核说accept，德国任务还是拒绝？

accept表示复核认为计划忠实表达了用户要求，不代表系统具备执行权限或数据。德国仍超出当前能力范围，由宿主阻断。语义理解与执行许可是两层判断。

### 为什么只给复核原问题和请求？

它需要判断用户想要什么、计划准备做什么；不应看到标准答案、历史成绩或评分结果，否则不能作为有效测试。它没有查询工具，也没有权限替用户修改计划。

### 为什么5/6不能放宽算6/6？

P03虽然不再放行错误计划，但用户仍没有得到需要补充哪些信息的具体追问。预先的门槛衡量业务完成，不只是安全停止；因此维持失败。
