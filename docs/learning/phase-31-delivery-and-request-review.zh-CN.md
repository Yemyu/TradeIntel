# Phase 31：报告写完和回答完整，是两件需要分别检查的事

这一轮发现并修复了两个程序问题：同一个输出目录重复使用可能改掉旧记录，以及报告还在最后修改时先记了“完成”。现在旧记录会保留，最终文件写好后再核对，核对时还能发现报告后来是否被改动。

你以后看到终端中断，不需要先重跑、重新输入密钥。已有目录可以只做检查：

```sh
.venv/bin/python scripts/run_unified_research.py --inspect 你的运行目录
```

complete且verified=true表示最终交付文件完整且与结束时一致；failed/interrupted表示记录了失败或中断；unconfirmed表示证据不足以确认完成；changed表示文件后来变化。核对本身不会调用GLM。

## 为什么全套测试通过后还能发现问题

测试只能覆盖写进测试里的情况。此前测了正常运行和一次中断，没有测“再次使用已有目录”和“报告最后写入失败”。这次增加故障注入：故意让这些地方失败，检查旧记录和完成标记是否仍可信。测试数量有参考价值，关键仍是覆盖了什么风险。

## 接下来AI部分要解决什么

例如你问：“查其他国家的进口金额，另外列出中国进口份额。”AI可能只记住第一项。程序随后把第一项做得完全正确，仍然没有完成你的全部问题。

我们本轮用一个故意漏写第二项的模拟计划，确认现有预览会放行。这说明需求清单需要补上：让AI逐项列出你要什么，程序把每项接到对应任务，暂时做不了的也列出来。

参考答案：**为什么不能再让AI自己写一句‘我已经全部回答了’？** 因为同一个模型可能没有意识到遗漏。下一阶段会核对原文位置、执行范围和清单，再由有参考答案的测试检查语义。即使原文每个字都被列入清单，也不能单凭这一点证明AI理解对了。

参考答案：**这是不是训练模型？** 没有更新模型参数。我们在改模型输入输出的组织方式，以及程序怎样检查和执行计划。能否让实际回答更好，还要在固定的新问题上验证。

本轮交付是可靠性修复与下一阶段的具体设计。需求清单尚未实现，新的真实模型整体成绩仍待验收；因果分析仍未获得可采纳结果。下一阶段Luna最高可按已确定规则实现，之后由Astra中审查完整性。
