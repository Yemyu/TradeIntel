# Phase 25 学习：为什么要记录任务来源、检索桥接和调用次数

> 后续审查更正：此轮记录只覆盖部分流程，未完成全部原定功能。超时计数、历史指纹等问题在[Phase 26](phase-26-integration-audit.zh-CN.md)解释并修复。下一步先补工程缺口，再安排真实模型验收。

## 先说这轮到底做了什么

这轮不是重新训练模型，也不是让 AI 自己做因果分析。我们把一个“用户问题 → 计划 → 查询 → 报告”的流程补上三种记账：

1. 用户到底问了哪几个独立问题；
2. 中文问题怎样帮助系统找到英文政策原文；
3. 哪个模型调用了几次、调用来自真实请求还是测试。

可以把它想成经济研究里的研究记录本。研究结论重要，但如果不知道样本、口径和处理步骤，别人就无法复核；AI 应用也是一样。

## 一、任务编号是什么

例如用户同时问“第一批政策何时生效”和“2018年9月与10月金额怎么比较”，系统现在会建三项记录：政策问题、贸易序列、贸易比较。

这里的关键是：

- “查到金额”只完成贸易序列；
- “计算了一个差值”才可能完成明确比较；
- 政策问题仍然要单独有证据和状态。

以前如果只看最后一份报告，很容易把“程序跑完”误解成“用户所有要求都完成”。`task_ids` 和 `obligations` 把两者分开。

## 二、为什么中文问题还要一个英文检索表达

本项目保存的政策公告正文主要是英文，而用户可以用中文提问。检索器需要找到相近的英文词，例如：

```text
initial Section 301 List 1 effective date additional duty rate
```

这句话只是“去哪里找”的路标，不是答案。真正回答仍然要引用公告原文，并保留用户的中文问题。报告会明确写出：桥接表达只用于找候选原文，不能替代原问题。

这和翻译事实不同：

- 翻译可以改变表达，但不能创造政策事实；
- 检索桥接可以增加命中机会，但不能证明命中的句子支持答案；
- 所以检索命中率和最终语义正确率是两个指标。

当前仍是 BM25 词法检索和有限正文语料，不是完整现行政策数据库，也没有因为加入桥接就宣称 RAG 验收通过。

## 三、调用账本记录什么

一次组合运行最多有两个模型阶段：

```text
规划模型：把中文问题整理成待确认计划
        ↓ 用户确认
政策回答模型：根据候选原文写带引用的草稿
```

贸易金额、变化率、缺失值和比较方向由固定程序计算，不算模型调用。`model-call-ledger.json` 会记录阶段、attempt_id、来源类型、调用次数、新 API 次数和受限元数据，但不会把 API 密钥或整段原始回答放进账本。

`fixture` 表示模拟测试，`live` 表示真实模型请求。两者不能混在一起，否则测试结果会被误读成真实模型成绩。没有调用政策模型时，也会明确记录 `no_model`，而不是把“没有调用”写成“回答成功”。

## 四、这轮测试说明什么

426项本地测试通过，说明请求格式、来源保存、桥接边界、调用计数和旧流程兼容性符合程序契约。它不能说明：

- 模型已经正确理解所有中文问题；
- 政策回答的每句话都经过人工语义验收；
- 因果识别已经成功；
- 已经完成微调、向量数据库或多智能体。

下一阶段要用 Astra 中审查一条真实整链案例，再决定是否做极小规模在线验收。

## 你需要记住的三句话

1. 任务编号解决“有没有漏答”；
2. 检索桥接解决“中文问题如何在英文原文里找候选”，不代替证据；
3. 调用账本解决“到底调用了什么、几次、是否是真实请求”。
