# Phase 10 学习版：AI 应用层到底要做什么

> 当前状态：设计已冻结；六个注册工具（五个模型查询工具 + 一个程序内部证据打包器）、证据包和确定性基线已实现并通过 60 道本地契约评估；下一步接入 LLM

## AI 应用不是“把模型接上数据库”

一个聊天模型本身不会可靠地读取数据库、计算百分比或判断因果。它擅长理解问题和组织语言，但可能算错数字、编造来源，或者把相关性说成因果。

所以 TradeShock AI 的做法是把工作拆开：

- Python/MySQL 做可重复的查询、计算和门槛检查；
- AI 选择已经登记的工具，并把工具结果翻译成人话；
- 工具返回证据和限制，AI 不能绕过这些限制。

## 什么是工具调用

工具调用就是给模型一份“可用函数清单”。模型看到用户问题后，不是自己假装知道答案，而是请求调用某个函数，例如 `get_descriptive_change`。程序执行函数，把结构化结果返回给模型，然后模型再写答案。

这和让模型直接写任意 SQL 不一样。任意 SQL 会带来注入、误查表和越权风险；固定工具可以检查参数、限制日期、固定公式并自动测试。

## 为什么先不用 LangChain/LangGraph

框架可以帮助组织工具和流程，但不能替代工具契约、数据质量和评估。如果还没有理解“输入是什么、输出是什么、失败时怎么办”，直接套框架只会把不清楚的流程包装起来。

第一版先用普通 Python 函数。等函数和测试稳定后，再判断框架是否真的减少了工作量。

## 六个注册工具各自回答什么

| 工具 | 作用 | 不允许做什么 |
|---|---|---|
| `get_policy_event` | 查政策名称、日期、税率和来源 | 不猜没有登记的政策 |
| `get_trade_series` | 查固定商品、国家和时间范围的序列 | 不接受任意 SQL |
| `get_descriptive_change` | 算同比、份额和变化 | 不把描述改叫因果 |
| `get_data_quality_status` | 查质量规则和阻断项 | 不隐藏失败规则 |
| `get_causal_readiness` | 查当前因果是否允许 | 不自行解除 blocked 状态 |
| `build_evidence_bundle` | 整理数值、公式、来源和限制 | 不生成没有来源的结论 |

其中前五个查询工具会作为 schema 提供给模型；`build_evidence_bundle` 不属于模型权限，由程序在核验真实成功结果后内部调用。这是“模型可以点菜，但不能伪造出餐记录”的边界。

## 目前项目为什么必须拒绝因果表述

当前配置状态是 `blocked_before_pretrend_v3`。这表示：资格层已经完成，但三次政策前匹配都没有满足条件，事件研究没有被允许。因此 AI 可以回答：

> 2018 年 8–12 月中国相关商品进口相对 2017 年同期下降了 23.7%。这是描述性变化；当前匹配门槛未通过，不能据此说关税导致了下降。

AI 不应该回答：

> 关税使中国进口下降了 23.7%。

后一句的问题不是措辞不好，而是超出了当前证据能支持的范围。

## 评估 AI 是否真的有用

我们会准备 60 道有标准答案的问题，不只截几张聊天图。要分别检查：

- 数值是否正确；
- 日期边界是否正确；
- 是否引用对应官方来源；
- 是否选择了合适的工具；
- 因果门槛失败时是否正确拒答。

直接问模型的版本是基准，接入确定性工具的版本是被测系统。目标不是让 AI 每个问题都说“可以”，而是让它在能回答时准确、不能回答时说清楚原因。

## 你需要学习的重点

你不需要先学会训练大模型。当前最重要的是理解：

- 什么是函数输入和输出契约；
- 为什么工具应该只读、参数有限；
- 为什么结构化证据比一段聊天文字更容易检查；
- 什么是 tool calling，和 RAG、Agent 分别是什么关系；
- 为什么评估要有标准答案、基线和停止门槛；
- 为什么“正确拒答”是可信 AI 的功能，而不是系统失败。
