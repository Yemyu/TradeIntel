## 先说结论

第二次运行的 8 道题全部正常结束，共 16 次模型请求，报告记录的总 token 为 34,905。程序层面的必要检查通过 6/8 题：事实和来源绑定正常，数字大多正确，但两个题目暴露了范围控制问题。

这说明 v2 的“程序展示证据、模型只负责选工具”方向是有效的，但当前还不能把它当成正式验收成绩，也不能把模型标记为已采纳。所有题目的 `manual_semantic_review`、`task_success_verified` 仍保持 `null/false`，这是有意保留的安全状态。

第一次尝试只发出 1 次请求后收到 HTTP 401，记录在 `20260907T174845344344Z.json`；它没有覆盖第二次完整结果，也不混入本次 8 题审查。

## 人工查看可见报告后的发现

### V201、V203、V208 基本达到目标

连续月份金额、三种原产地金额及其来源都出现了；V203 的三个数满足中国 + 其他原产地 = 全部原产地；V208 明确展示了 `pass_with_review`、2 条复核规则和 0 条失败规则，没有把“需复核”说成无条件通过。

### V202 暴露了真正的范围错误

问题只要求 2019 年 2 月、5 月和 11 月，但模型调用了 2019 年 2 月至 11 月的连续区间，程序因此返回了中间月份。可见报告没有生成“只对这三个指定月份求和”的事实，范围检查也失败。模型草稿里的三月合计还少了 1,000 美元；草稿没有发布到用户界面，但它说明不能信任自由文本自行算合计。

### V204 数值正确，但工具多查了一整段月度数据

登记的同期比较工具给出了正确的基期、当期和 11.5291% 变化；模型随后又调用了一个 2017-01 到 2018-05 的宽范围月度工具。这个额外查询没有改变核心数值，却违反了本试验要求的精确范围，说明模型还不知道“已经有专门比较工具时，不要再扩大查询”。

### V205、V206、V207 说明“有事实”不等于“完成任务”

程序报告确实展示了 818、315、284 三个数，也展示了 2018-11 金额、政策实际日期和税率。但当前版本不会发布模型自由撰写的解释，因此可见报告没有完整呈现：

- 818、315、284 为什么属于不同筛选阶段；
- 2015-01 为什么不可查询；
- 便签中的 2018-07-01 和 30% 为什么与登记事实不一致。

模型草稿里有部分这些解释，但草稿被明确标记为 `draft_for_audit_only`，不能冒充经过验证的用户答案。这是当前输出架构的缺口，不是把草稿偷偷当成通过答案的理由。

## 这次试验教会我们的概念

“结构正确”可以理解为考试答题卡上的数字和题号填对了；“语义完整”还要看有没有回答问题中的解释、缺失原因和限制条件。当前 v2 已经把第一件事做得比较可靠，但第二件事仍然需要一个受证据约束的任务完成层。

“查询范围过宽”也不一定会立即造成数字错误，却会带来两个风险：用户可能误把中间月份纳入合计；系统花费额外请求和 token；评估时难以证明模型只使用了问题允许的数据。因此 V202、V204 不能只看最终几个数字是否碰巧正确。

## 阶段门结论

本阶段门要求 8/8 题同时满足自动检查和人工完整性检查。实际结果为自动 6/8，且 V202、V204 有范围问题，V205–V207 的可见解释不完整，因此**不进入正式验收设计**，也不更新模型采纳状态。

## 下一阶段方案

下一阶段做 v2.1 的定向修复，仍保留本次原始结果：

1. 给月度工具增加显式的 `months` 参数和范围互斥规则，让不连续月份只能查询指定月份；
2. 增加确定性的任务覆盖模板，针对“为什么不能混为一谈”“某年月不可查”“核对错误便签”等解释，只从已登记事实生成可见说明；
3. 为这两个修复各增加离线测试，再建立新的运行指纹；
4. 重新运行同一组 8 题，只有自动和人工都通过，才设计正式独立验收集。
