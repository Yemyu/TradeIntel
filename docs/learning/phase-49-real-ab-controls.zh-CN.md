# Phase 49：真正的 A/B 对照和“完成”到底代表什么

> 0117更新：下面的“事实召回”“acceptance_ready=true”和“完整冻结”解释已被复审更正。程序搜到“25%”并不知道一句话在肯定还是否定它；现在只能记字面命中，答案需要另审。离线完成改叫synthetic_protocol_completed，acceptance_ready保持false。A能复核查出的数，但还需要一份独立设定的查询条件来核对是否查错国家、商品或时间。下一步就是把这两种检查补齐，详见[0117](../decisions/0117-acceptance-reaudit.zh-CN.md)。

## 先说结论

这一步没有调用 GLM，也没有新增 API 成本。我们修的是“项目怎么证明自己做对了”，不是让模型突然变聪明。

现在一个离线合成案例只有在下面几件事都成立时，才会出现 `acceptance_ready=true`：

1. 计划审核通过；
2. 实际交付文件完整，而且审核前后哈希没有变化；
3. 答案审核通过；
4. 适用的 A/B 控制真的运行过，并且记录绑定到了同一个问题。

单独把状态写成 `accepted`，或者放一个写着 `status=validated` 的文件，都不算完成。

## A 是什么？——检查“算数链路”

A 用在贸易金额问题上。

主流程会经过工作流和工具得到金额。A 再绕开主流程里的计算函数，直接读取已经声明的源表 `data/processed/analysis/policy_case_monthly.csv`，按同样的月份和原产地重新求和，然后比较：

- 每个月的金额是否相同；
- 总额是否相同；
- 源表文件的 SHA256 是否被保存。

所以 A 不是“再问一次模型”，而是“用另一条简单的计算路径复核主结果”。如果两边不一样，运行器会停止，不会把结果标成成功。

## B 是什么？——检查“检索证据到底带来多少帮助”

B 用在政策问题上。

主组会把政策检索片段交给模型，让模型生成带引用的回答。B 保留同一个问题和历史范围，但不把检索片段和工具传给模型，然后保存模型实际返回的文字。

程序只统计登记事实在 B 回答中出现了多少，并把结果写成 `baseline_gap` 或 `pass`。这里的 `baseline_gap` 不是程序失败，而是一个有意义的实验结果：它说明“没有文档时模型少答对了哪些事实”。我们不能先命令模型拒答，再把拒答包装成 RAG 成功。

## 为什么还要保存模型消息？

因为只看最终结果不够。保存消息可以检查：

- 模型工厂有没有拿到参考答案；
- B 是否真的没有收到 `evidence`；
- 运行时使用的工具列表是什么；
- 以后复查时，输入是否和当时一致。

参考答案只给审核程序，不给模型。这样才能避免“把答案泄漏给模型后再测准确率”。

## `acceptance_ready` 不是准确率

`acceptance_ready=true` 的含义是：这次离线运行的审核、交付和控制记录彼此对得上，可以被追溯。

它不代表：

- GLM 在新问题上的准确率；
- RAG 已经覆盖所有政策文件；
- 因果分析已经成立；
- 可以直接把这次结果写成线上产品成绩。

因此当前仍不启动新的在线题集，也不需要你输入 API key。下一阶段先由高推理模型审查这套边界，再决定是否做不联网预检。

## 可以自己查看什么

如果以后运行离线案例，重点看这些文件：

- `controls/<案例>-control-a.json`：A 的独立复算；
- `controls/<案例>-control-b.json`：B 的真实无证据回答和事实缺口；
- `reviews/`：计划审核、答案审核和审核决定；
- `responses/`：模型消息、回答和安全用量元数据；
- `ledger.json`：调用顺序、停止原因和最终绑定；
- `run-summary.json`：本次运行的总结果。

这些文件的共同作用是让我们回答一个简单问题：**到底做了什么、用的是什么输入、哪一步通过、哪一步没有通过？**
