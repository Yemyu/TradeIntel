### 1. 为什么不能只把 fixture 换成 GLM？

因为这样会把两件事混在一起：流程是否正常，和模型回答是否真的有效。现在账本会明确写：

| 模式 | 是否访问模型服务 | 审核标签 | 能说明什么 |
| --- | --- | --- | --- |
| `synthetic` | 否 | `fixture` | 程序边界、文件和账本能否复现 |
| `live_development` | 是（但有界） | `ai_assisted` | 真实模型在四个已知问题上的集成表现 |

所以离线演示里的“通过”不能填进真实成绩表，真实批次也不能反过来修改离线事实。

### 2. 为什么规划和政策回答要分开预算？

一次用户问题通常先有“理解问题并列计划”的规划调用，再有“根据证据生成政策主张”的回答调用；政策 B 还会用同一问题、同一模型设置、去掉证据再调用一次。把阶段预算分开，才能知道钱和 token 用在哪里，也能防止模型在失败后无限重试。

真实开发默认是：4 次规划 + 2 次带证据回答 + 2 次无证据回答；累计已报告 20,000 tokens 后停止。未知用量也停止，因为不知道成本就不能诚实地继续。

### 3. 审核人为什么不能是模型自己？

模型生成答案，宿主程序和审核器再读取这个“实际答案包”。审核器只使用实际计划、交付和证据做检查，并把标签写成 `ai_assisted`。这能发现结构错、范围错、没有引文等问题，但它不是第三方盲审，所以项目仍保留 `semantic_accuracy_measured=false`。

### 4. 为什么要有四个已知场景？

四题分别检查不同边界：

1. 贸易比较：模型是否把自然语言变成正确的月份、国家范围和比较方向；
2. 政策日期与税率：主组是否引用正确的官方片段；
3. 政策 + 贸易：两个子任务能否在一次交付中同时完成；
4. 信息不足：模型是否会先澄清，而不是擅自猜商品、月份或指标。

这四题只是集成开发样例，不是“模型对所有问题准确率 100%”。

## 你可以怎样运行

先做零网络预检：

```bash
source .venv/bin/activate
export TRADEINTEL_MODEL_BASE_URL='https://open.bigmodel.cn/api/paas/v4'
export TRADEINTEL_MODEL_NAME='你的模型名'
export TRADEINTEL_MODEL_API_KEY='本地设置的密钥'
PYTHONPATH=src python scripts/run_live_development_0128.py \
  --output /tmp/tradeintel-live-preflight-0128
```

预检不会调用模型，也不会创建输出目录。只有看清模型名、端点、预算后，才可以在一个全新的路径执行：

```bash
PYTHONPATH=src python scripts/run_live_development_0128.py \
  --output /tmp/tradeintel-live-run-首次尝试 --execute
```

如果终端提示 token 未知、连接失败、JSON 格式错或答案主张无法绑定来源，批次会停在账本里。不要把同一目录再跑一遍；先看停止原因，再决定是否需要 Astra 重新判断方案。

## 这一步没有做什么

- 没有训练或微调模型；
- 没有实现多智能体；
- 没有把因果分析重新判为成功；
- 没有把 AI 辅助审核冒充人工独立金标；
- 没有把任何 API key 写入项目。

本阶段的价值是把“真实模型能不能接入、能否留下可审计证据、失败时能否及时停下”变成一个可以实际检查的问题。
