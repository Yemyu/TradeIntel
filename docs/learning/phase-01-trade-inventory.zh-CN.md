# 第 1 阶段：盘点第一份真实贸易数据（中文版）

> 这是一份学习说明，不要求你手写代码。程序由 AI 编写，你需要理解数据的含义、选择和验证方法。

## 1. 这一步解决什么问题

政策清单只告诉我们“哪些商品被列入 List 1”。它不能告诉我们每个月美国实际从哪些国家进口了多少。

因此我们先取得 Census 的一份真实月度进口档案，只做盘点：

- 文件是否完整；
- 一行数据代表什么；
- 数据覆盖哪个月份；
- 哪些字段能支持我们的研究；
- 原始记录需要怎样汇总。

这一步还不回答“关税是否造成了变化”。

## 2. 这份文件和普通 CSV 有什么不同

下载的 ZIP 里面有一个 `IMP_DETL.TXT`。它是**定长文本**（fixed-width text）：每个字段占用固定的字符位置，而不是用逗号分隔。

例如一行的前几段依次是：

| 位置 | 内容 |
|---|---|
| 1–10 | 10 位 HTS 商品编码 |
| 11–14 | 4 位原产国代码 |
| 23–26 | 年份 |
| 27–28 | 月份 |
| 74–88 | 进入消费的进口金额 |

“固定位置”是来源方的数据格式决定的，不是我们随便选择的代码写法。AI 可以负责按位置读取，但人必须知道每个位置的业务含义。

## 3. 为什么一行还不能直接用于分析

原始一行还拆分到了国家子代码、入境地区和税率条款等更细的层级。同一个“商品 × 国家 × 月份”可能有多行。

所以我们需要把相同的：

> 商品编码 + 原产国 + 月份

的金额加总，才能得到分析表中的一行。

这就是“汇总粒度”（grain）的概念：**先声明一行代表什么，再决定哪些原始行应该合并。**

## 4. 本次盘点结果

使用 2018 年 7 月档案后，得到：

- 原始明细：1,716,983 行；
- 与 List 1 清单匹配：305,647 行；
- 匹配后的商品—国家组合：36,531 组；
- 覆盖 211 个原产国；
- 818 个政策税号中，812 个当月出现了贸易记录，6 个没有记录；
- 所有匹配记录的进入消费金额合计约 395.6 亿美元；
- 其中中国约 25.7 亿美元。

“6 个税号没有记录”只说明这个月没有观察到对应贸易记录。它不等于数据缺失，也不等于商品永远没有贸易。

程序另外生成了一张按“商品 × 国家 × 月份”汇总的样例表。它把原始 30 多万行压缩成每个组合一行，后续的 48 个月分析面板会沿用这个粒度。

## 5. AI 做什么，人做什么

AI 负责：

- 从 ZIP 中读取定长文本；
- 按官方字段位置解析；
- 用已审核的 818 个税号筛选；
- 汇总金额；
- 生成报告和测试。

你需要负责理解和检查：

- 为什么选择“进入消费金额”这个口径；
- 为什么不能把一行直接当作商品—国家—月份；
- 为什么“没有记录”和“数据缺失”不同；
- 这个盘点结果为什么还不能证明政策造成了变化。

## 6. 本阶段的验收

你不需要背固定位置，也不需要记住 Python 语法。你只需要能够说明：

1. 政策表和贸易表分别回答什么问题；
2. 为什么原始贸易明细需要汇总；
3. 为什么金额口径必须在数据契约中明确；
4. 为什么一次月度盘点不能直接推出因果结论。

这一步已经完成。项目已按同一规则整理 2016–2019 年共 48 个月，并为每个月保存了来源和校验信息；下面的规则说明了这批数据是怎样可靠地生成的。

## 7. “你需要能够解释的内容”：参考答案

### 1. 政策表和贸易表分别回答什么问题？

政策表描述“规则”：哪项政策、针对谁、什么时候生效、涉及哪些商品。贸易表描述“事实记录”：每个月美国从哪个原产国进口了哪些商品、金额是多少。前者不能替代后者，后者也不会自动告诉我们政策背景。

### 2. 为什么原始贸易明细需要汇总？

原始档案的一行可能只是一个更细的申报或统计分拆。同一个商品、国家和月份可以出现多行。如果直接把每行当成一个分析观察值，就会重复计算金额或让同一组合出现多次。先声明“一行代表商品 × 原产国 × 月份”，再按这个粒度汇总，后续查询才有稳定含义。

### 3. 为什么金额口径必须在数据契约中明确？

“进口金额”可能有不同统计口径，例如进入消费金额、海关价值或包含保险运费的金额。它们回答的问题不同，数值也不能混加。数据契约把本项目使用的字段和单位固定下来，避免不同脚本或不同来源在没有提醒的情况下混用。

### 4. 为什么一次月度盘点不能直接推出因果结论？

盘点只能证明某个月观察到了哪些记录和金额。即使政策之后金额下降，也可能同时受到季节性、需求、汇率、其他政策或数据口径变化影响。要讨论因果，需要明确的对照组、趋势假设和更严格的研究设计；数据盘点本身没有提供这些保证。

## 8. 为什么不长期保存所有 ZIP

48 个月的官方压缩包合计约 7.5GB。对本项目来说，长期保存它们的收益不高：它们是公开的历史文件，网址可以重新下载。

因此采用下面的保存策略：

- 下载时暂存在本地，保证读取过程可以重复检查；
- 结果表记录官方 URL、文件名和 SHA-256 校验值；
- 处理成功后可以删除本地压缩包，不把它们提交到 GitHub；
- 如果以后发现解析错误或官方修订，只要重新下载并比较校验值即可。

网址回答“去哪里找”，校验值回答“找回来的是否还是同一个文件”。两者一起才构成可靠的来源追溯。

## 9. 48 个月面板已经生成

整理全部历史数据时，程序会按月份循环：下载一个月、读取并汇总、写入该月结果、记录来源校验，然后再处理下一个月。这样即使中途停止，也能从已完成月份继续；重复运行不会把同一个月的数据追加两遍。

本次运行已经完成上述流程：

- 来源清单：`data/processed/trade/source_manifest.csv`，共 48 个月；
- 每月结果：`data/processed/trade/monthly/`，共 48 个 CSV；
- 合并面板：`data/processed/trade/trade_import_monthly.csv`，共 1,600,952 行聚合记录；
- 原始 ZIP：处理后已清理，之后仍可根据来源 URL 和 SHA-256 重新取得并核对。

下一步不是马上让 AI 猜政策效果，而是把已经验证的结果放入 MySQL，学习如何用表结构、主键和 SQL 查询管理它们。之后才继续讨论更复杂的政策分析。
