# Phase 10p：给AI一套可靠的执行流程

## 这一步做了什么

新建了独立开发流程 `structured_workflow.py`，把“能力检查—选工具—执行—核对结果—发布”连起来。已跑通本地商品计数示例，不需要密钥，也没有新增模型费用。

**它还不是完整的新AI助手。** 这一阶段输入的是已经明确的结构化请求，不是用户随意说的一句话。旧v2.1入口、48份验收结果和75%的任务通过率保持不变。

## 从用户问题到结果，分工在哪里

| 环节 | 意思 | 当前状态 |
|---|---|---|
| 理解问题 | 把“查哪些月份、哪个国家、要什么指标”整理清楚 | 还需单独设计、验证模型解析 |
| 检查能力 | 判断所需数据与操作是否被本系统支持 | 已接入开发流程 |
| 执行工具 | 按登记任务读取数据，不任意编写SQL | 已接入；宿主固定编排 |
| 核对结果 | 检查返回月份、国家、金额合计是否符合明确请求 | 已接入贸易查询检查 |
| 发布结果 | 只发布工具证据或有依据的拒绝，不放行自由草稿 | 已接入开发流程 |

这里的“宿主”就是我们写的程序。新流程由程序选工具，不能宣传成模型自己选对了工具。

## 已经解决到哪一步

- 商品计数：固定查询政策清单与匹配准备状态，提供三个计数及口径区别，不再只查其中一个来源。
- 匹配进度：只查准备状态，不额外取无关贸易长窗口。
- 德国企业、GDP、删除操作：对明确的结构化请求，直接给出具体能力限制，不替换成其他原产地总额。
- 全部月份超范围：直接说明未查询金额，未知不是零，不强制先成功查数据才能拒绝。
- 部分月份超范围：实际查询，未知保留null，可查月份明确列出。
- 返回错范围、重复月份、异常合计或工具失败：停止发布金额，但仍向用户说明执行失败，不再只有空答案。

不支持的混合任务或多余字段会要求澄清，不会偷偷忽略某一部分。当前只支持一个明确任务，不能说已完成复杂多任务Agent。

## 你需要能够解释的问题与参考答案

**1. 为什么不直接让大模型自己决定所有步骤？**

因为有些步骤是已知的业务规则。例如要解释三个商品计数，就一定需要政策和匹配两类证据。把这个规则写进程序能减少遗漏；模型更适合帮助理解用户表达，而不是每次重新猜业务流程。

**2. 结构化请求是什么？我要学习怎么写代码吗？**

可以把它理解成一张填写完整的业务表单：国家、月份、指标、商品粒度、是否要求因果判断。你需要理解这些字段代表什么，不需要背JSON语法。将来AI可以帮你填，但填得是否符合原问题必须验证。

**3. 检查通过，为什么仍写“用户意图未验证”？**

因为程序可以确认“这张表单能执行”，却不能确认“这就是用户想要的”。如果AI把德国填成中国，表单合法仍然答错了。因此下一步要验证自然语言到表单的映射。

**4. 为什么拒绝也算系统能力？**

真实系统不可能拥有所有数据。明确说明缺什么、没有执行什么，通常比给一个看似完整但换了范围的答案更可靠。但这次拒绝测试通过不代表真实语言下的拒绝准确率已经通过验收。

**5. 单元测试通过，能直接写简历“准确率100%”吗？**

不能。单元测试用于检查人为明确的输入和故障条件；它不是独立用户问题的准确率。正式效果还要用未用于调试的问题测试整个AI流程。
