# Phase 30：看懂一次运行有没有超预算、有没有真正交付

这一阶段不是再给 AI 加一个新按钮，而是把“运行记录”补完整。以前我们能看到模型调用账本，但还不够清楚：本次最多允许调用几次？用的是什么模型配置？如果中途退出，哪些文件已经写好？

## 1. 预算是什么

预算就是事先写下的上限，不让程序因为失败而无限重试。本项目现在的上限很简单：

| 环节 | 最多调用 | 意思 |
|---|---:|---|
| 规划 | 1 次 | 把中文问题整理成待确认计划 |
| 政策回答 | 1 次 | 依据检索到的政策原文生成草稿 |
| 一次运行合计 | 2 次 | 两个环节相加的总上限 |

贸易金额、比较和百分比由固定程序计算，不消耗模型调用。超时后不自动换模型、不自动换 key、不自动再试；这样日志才能告诉我们第一次到底发生了什么。

## 2. 配置快照是什么

配置快照不是把密钥保存下来，而是留下足够复盘的信息，例如：

- 这一步是 `fixture`（离线样例）、`live`（真实模型）还是 `no_model`；
- 使用的适配器和模型名；
- 服务端点的主机/路径；
- 超时和温度；
- 明确写着 API key 没有被记录。

它解决的是“同一个项目为什么这次结果不一样”的第一层排查问题，同时避免把凭据写进 GitHub 或运行目录。

## 3. 交付状态和业务状态不是一回事

业务状态回答“研究任务怎么样”，例如 `research_draft`、`partial` 或 `policy_failed`。交付状态回答“文件有没有完整落地”。

例如政策模型超时，贸易报告、结果文件和审计文件仍然可能完整写出：业务状态是 `partial`，文件交付状态可以是 `complete`。相反，如果电脑在写报告前中断，业务结果可能还没有形成，交付状态就是 `interrupted`，并列出缺少的文件。

运行目录旁的 `run.delivery-intent.json` 是开始前的登记；目录内的 `delivery-status.json` 是结束时的核对。两者都不提供自动恢复，只是防止“看起来跑过了”却不知道实际留下了什么。

## 4. 这一阶段没有做什么

没有训练模型、没有微调 Transformer、没有新增 RAG 语料、没有重新做因果匹配，也没有调用在线 API。它是 AI 工程中的可靠性基础：先能说清一次运行的边界和产物，再谈真实模型效果。

## 5. 你可以怎样检查

打开一次运行目录，先看三个文件：

1. `model-call-ledger.json`：每个模型阶段调用了几次；
2. `delivery-status.json`：应有文件、已写文件和缺失文件；
3. `unified-result.json`：业务结果、预算检查和配置快照。

如果 `delivery-status.status` 是 `complete`，只说明必需文件都在，不等于因果结论成立，也不等于 AI 语义准确率已经通过验收。
