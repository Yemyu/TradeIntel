# 第 3 步：用 MySQL 管理已经验证的数据（中文版）

> 这是进入数据库前的学习讲义。你不需要先写 SQL，也不需要现在安装任何东西。

目前环境检查已经确认：本机安装了 MySQL 9.7，服务在运行；`root@localhost` 登录成功，并已配置本机的 `tradeintel` 安全登录路径。密码不需要发到聊天中。

## 1. 这一步解决什么问题

目前的结果已经保存在 CSV 中。CSV 适合交换和查看，但它只是一个平面文件：它不会主动保证一行是否重复，也不会保证政策商品一定对应某个真实政策。

MySQL 是一个可以管理多张相关表的数据库系统。它让我们能够：

- 用主键明确一行数据的身份；
- 用外键保证表之间的关联存在；
- 用 SQL 重复查询同一口径，而不是每次重新写文件处理代码；
- 在导入时发现重复、缺失或类型错误；
- 为后面的 AI 工具提供稳定、可控的查询入口。

这不是为了“显得技术复杂”，而是把已经验证过的数据放进一个有规则的容器。

## 2. CSV 和数据库的区别

可以把 CSV 理解成一张不会主动提醒你的电子表格，把 MySQL 理解成一个会执行规则的资料库：

| 概念 | CSV | MySQL |
|---|---|---|
| 数据组织 | 一个文件一张平面表 | 多张表可以互相连接 |
| 重复检查 | 需要程序自己检查 | 可以用主键约束 |
| 关联关系 | 只靠约定的列名 | 可以用外键表达 |
| 查询 | 通常先读入 Python | 直接用 SQL 筛选、汇总和连接 |
| 适合场景 | 快照、交换、版本记录 | 可重复查询、应用服务、多人使用 |

CSV 不是“低级”格式，数据库也不是“自动正确”。数据库只能执行我们给它的规则；如果表设计错了，错误仍然会被保存。因此这一阶段最重要的是理解表的含义，而不是记住 SQL 拼写。

## 3. 第一版只设计三张核心表

我们先使用足够清楚、又能支持项目的最小结构：

### `policy_event`：政策事件表

一行代表一项政策事件。当前只有 Section 301 List 1 一行，包含政策名称、目标原产国、生效日期、税率和来源网址。

### `policy_product`：政策商品表

一行代表“一项政策中的一个 HTS8 商品”。它通过 `policy_id` 关联到 `policy_event`，同时保存原始代码、规范代码、来源页码和修订状态。

### `trade_monthly`：月度贸易事实表

一行代表：

> 一个自然月 + 一个原产国 + 一个 HTS10 商品

它保存月份、国家代码、HTS10/HTS8、进入消费金额、明细行数和来源校验值。48 个月的贸易面板大约有 160 万行，后续的描述性分析和 AI 查询都从这里读取。

## 4. 为什么贸易表使用组合主键

这张表没有单独依赖一个“看起来唯一”的流水号，而是使用：

> `year + month + origin_code + hts10`

作为组合主键。

原因是这正是业务上“一行”的定义。如果同一个月份、同一个国家、同一个 HTS10 被导入两次，数据库应该直接拒绝，而不是悄悄保存两行再让我们猜哪一行是真的。

这就是数据粒度和主键的关系：先决定一行代表什么，再让主键保护这个定义。

## 5. 为什么需要外键

`policy_product.policy_id` 应该指向 `policy_event.policy_id`。外键表达的是：

> 不能出现一个找不到对应政策的政策商品。

它不是为了让查询变复杂，而是把业务规则交给数据库持续检查。以后增加第二项政策时，同一套结构仍然能复用。

## 6. 为什么不把所有内容塞进一张大表

如果每一条贸易记录都重复写政策名称、税率和政策来源：

- 数据量会变大；
- 同一政策改名或修订时要改很多行；
- 不同行可能出现互相矛盾的政策信息；
- 很难分辨错误来自政策表还是贸易表。

拆成“事件—商品—贸易事实”三张表后，政策信息只保存一次，贸易记录只保存贸易事实，查询时再用 `JOIN` 临时组合。这个设计比“看起来只有一张表”更容易验证。

## 7. MySQL、SQLite 和 Docker 怎么选

| 方案 | 优点 | 代价 | 本项目决定 |
|---|---|---|---|
| 只用 CSV | 不需要安装任何东西 | 没有数据库约束，查询依赖脚本 | 作为来源和快照保留 |
| SQLite | 轻量、单文件、容易演示 | 服务器和权限经验较少 | 不作为主要学习目标 |
| 本机 MySQL | 延续你已有的 SQL 知识，能展示真实数据库能力 | 需要确认本机服务是否运行 | **首选** |
| Docker 中 MySQL | 环境可复现 | 还要学习容器、端口和卷 | MySQL 跑通后再考虑 |

我们的顺序是先检查本机是否已有 MySQL。若没有，再一起决定是否使用 Docker 或其他方式；不会在你不知情的情况下把一堆服务安装到系统环境。

## 8. AI 做什么，人做什么

AI 负责：

- 起草建库、建表和导入脚本；
- 把 CSV 的字段映射到数据库字段；
- 编写查询和自动对账测试；
- 处理批量导入的重复运行和错误报告。

你需要负责理解和检查：

- 每张表的一行代表什么；
- 主键为什么能阻止错误重复；
- 外键表达的业务规则是什么；
- 查询出来的总额、行数和月份是否符合现实含义。

## 9. 你需要能够解释的内容：参考答案

### 1. 数据库、表、行和列分别是什么？

数据库是一个可以管理相关数据的整体容器；表是其中一种主题明确的数据集合；行是一条记录；列是这条记录的一个属性。例如 `trade_monthly` 是表，一行是一个“月 × 国家 × 商品”观察值，`import_value_consumption_usd` 是其中一列。

### 2. 为什么贸易表需要组合主键？

因为业务上决定一行身份的不是一个随机编号，而是月份、国家和商品的组合。组合主键把业务定义变成数据库规则，使同一个观察值重复导入时立即暴露。

### 3. 外键解决什么问题？

外键保证一个表中的关联值在另一个表中确实存在。例如政策商品必须属于一项已登记的政策，不能出现孤立商品记录。

### 4. 为什么不把三张表合成一张？

因为政策信息和贸易事实的变化频率、含义和数量都不同。拆表可以减少重复、避免矛盾，并让每一张表的一行含义更清楚；需要一起查看时再用 `JOIN`。

### 5. CSV 已经能分析，为什么还要 MySQL？

CSV 证明了数据可以保存和交换，MySQL 则增加了约束、关联和可重复查询能力。项目需要展示的不只是“算出一个数字”，还包括“数字被怎样可靠地管理”。不过 MySQL 不会替代 CSV：CSV 仍作为来源快照和结果交换格式。

## 10. 下一步任务澄清

真正开始时按下面顺序进行：

1. 只读检查本机是否已有 MySQL 服务和可用连接；
2. 先创建三张表，不导入全部大数据；
3. 用政策事件、818 个政策商品和 2018 年 7 月单月贸易文件（36,531 条记录）做小规模验证；
4. 执行十条能够解释的 SQL 查询并对账；
5. 小规模结果正确后，再批量导入 160 万行贸易面板；
6. 比较 CSV 和 MySQL 的行数、金额总额、最早/最晚月份，确认迁移没有改变结果。

本次 CSV 导入使用了 `LOAD DATA LOCAL INFILE`。MySQL 服务器默认关闭这个本地文件开关，因此导入期间临时打开，完成后已关闭；它只影响文件传输方式，不改变数据内容。完成标准是“数据库中的结果与已经验证的 CSV 一致”，而不是“安装完 MySQL 就算完成”。这一阶段暂时不接 AI Agent、不引入 dbt，也不要求你手写导入代码。
