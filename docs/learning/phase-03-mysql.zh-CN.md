# 第 3 步：用 MySQL 管理已经验证的数据（中文版）

> 这是进入数据库前的学习讲义。你不需要先写 SQL，也不需要现在安装任何东西。

目前环境检查已经确认：本机安装了 MySQL 9.7，服务在运行；`root@localhost` 登录成功，并已配置本机的 `tradeintel` 安全登录路径。密码不需要发到聊天中。

## 1. 这一步解决什么问题

目前的结果已经保存在 CSV 中。CSV 适合交换和查看，但它只是一个平面文件：它不会主动保证一行是否重复，也不会保证政策商品一定对应某个真实政策。

MySQL 是一个可以管理多张相关表的数据库系统。它让我们能够：

- 用主键明确一行数据的身份；
- 用外键保证表之间的关联存在；
- 用 SQL 重复查询同一口径，而不是每次重新写文件处理代码；
- 在导入时发现重复、缺失或类型错误；
- 为后面的 AI 工具提供稳定、可控的查询入口。

这不是为了“显得技术复杂”，而是把已经验证过的数据放进一个有规则的容器。

## 2. CSV 和数据库的区别

可以把 CSV 理解成一张不会主动提醒你的电子表格，把 MySQL 理解成一个会执行规则的资料库：

| 概念 | CSV | MySQL |
|---|---|---|
| 数据组织 | 一个文件一张平面表 | 多张表可以互相连接 |
| 重复检查 | 需要程序自己检查 | 可以用主键约束 |
| 关联关系 | 只靠约定的列名 | 可以用外键表达 |
| 查询 | 通常先读入 Python | 直接用 SQL 筛选、汇总和连接 |
| 适合场景 | 快照、交换、版本记录 | 可重复查询、应用服务、多人使用 |

CSV 不是“低级”格式，数据库也不是“自动正确”。数据库只能执行我们给它的规则；如果表设计错了，错误仍然会被保存。因此这一阶段最重要的是理解表的含义，而不是记住 SQL 拼写。

## 3. 第一版只设计三张核心表

我们先使用足够清楚、又能支持项目的最小结构：

### `policy_event`：政策事件表

一行代表一项政策事件。当前只有 Section 301 List 1 一行，包含政策名称、目标原产国、生效日期、税率和来源网址。

### `policy_product`：政策商品表

一行代表“一项政策中的一个 HTS8 商品”。它通过 `policy_id` 关联到 `policy_event`，同时保存原始代码、规范代码、来源页码和修订状态。

### `trade_monthly`：月度贸易事实表

一行代表：

> 一个自然月 + 一个原产国 + 一个 HTS10 商品

它保存月份、国家代码、HTS10/HTS8、进入消费金额、明细行数和来源校验值。48 个月的贸易面板大约有 160 万行，后续的描述性分析和 AI 查询都从这里读取。

## 4. 为什么贸易表使用组合主键

这张表没有单独依赖一个“看起来唯一”的流水号，而是使用：

> `year + month + origin_code + hts10`

作为组合主键。

原因是这正是业务上“一行”的定义。如果同一个月份、同一个国家、同一个 HTS10 被导入两次，数据库应该直接拒绝，而不是悄悄保存两行再让我们猜哪一行是真的。

这就是数据粒度和主键的关系：先决定一行代表什么，再让主键保护这个定义。

## 5. 为什么需要外键

`policy_product.policy_id` 应该指向 `policy_event.policy_id`。外键表达的是：

> 不能出现一个找不到对应政策的政策商品。

它不是为了让查询变复杂，而是把业务规则交给数据库持续检查。以后增加第二项政策时，同一套结构仍然能复用。

## 6. 为什么不把所有内容塞进一张大表

如果每一条贸易记录都重复写政策名称、税率和政策来源：

- 数据量会变大；
- 同一政策改名或修订时要改很多行；
- 不同行可能出现互相矛盾的政策信息；
- 很难分辨错误来自政策表还是贸易表。

拆成“事件—商品—贸易事实”三张表后，政策信息只保存一次，贸易记录只保存贸易事实，查询时再用 `JOIN` 临时组合。这个设计比“看起来只有一张表”更容易验证。

## 7. MySQL、SQLite 和 Docker 怎么选

| 方案 | 优点 | 代价 | 本项目决定 |
|---|---|---|---|
| 只用 CSV | 不需要安装任何东西 | 没有数据库约束，查询依赖脚本 | 作为来源和快照保留 |
| SQLite | 轻量、单文件、容易演示 | 服务器和权限经验较少 | 不作为主要学习目标 |
| 本机 MySQL | 延续你已有的 SQL 知识，能展示真实数据库能力 | 需要确认本机服务是否运行 | **首选** |
| Docker 中 MySQL | 环境可复现 | 还要学习容器、端口和卷 | MySQL 跑通后再考虑 |

我们的顺序是先检查本机是否已有 MySQL。若没有，再一起决定是否使用 Docker 或其他方式；不会在你不知情的情况下把一堆服务安装到系统环境。

## 8. AI 做什么，人做什么

AI 负责：

- 起草建库、建表和导入脚本；
- 把 CSV 的字段映射到数据库字段；
- 编写查询和自动对账测试；
- 处理批量导入的重复运行和错误报告。

你需要负责理解和检查：

- 每张表的一行代表什么；
- 主键为什么能阻止错误重复；
- 外键表达的业务规则是什么；
- 查询出来的总额、行数和月份是否符合现实含义。

## 9. 你需要能够解释的内容：参考答案

### 1. 数据库、表、行和列分别是什么？

数据库是一个可以管理相关数据的整体容器；表是其中一种主题明确的数据集合；行是一条记录；列是这条记录的一个属性。例如 `trade_monthly` 是表，一行是一个“月 × 国家 × 商品”观察值，`import_value_consumption_usd` 是其中一列。

### 2. 为什么贸易表需要组合主键？

因为业务上决定一行身份的不是一个随机编号，而是月份、国家和商品的组合。组合主键把业务定义变成数据库规则，使同一个观察值重复导入时立即暴露。

### 3. 外键解决什么问题？

外键保证一个表中的关联值在另一个表中确实存在。例如政策商品必须属于一项已登记的政策，不能出现孤立商品记录。

### 4. 为什么不把三张表合成一张？

因为政策信息和贸易事实的变化频率、含义和数量都不同。拆表可以减少重复、避免矛盾，并让每一张表的一行含义更清楚；需要一起查看时再用 `JOIN`。

### 5. CSV 已经能分析，为什么还要 MySQL？

CSV 证明了数据可以保存和交换，MySQL 则增加了约束、关联和可重复查询能力。项目需要展示的不只是“算出一个数字”，还包括“数字被怎样可靠地管理”。不过 MySQL 不会替代 CSV：CSV 仍作为来源快照和结果交换格式。

## 10. 从登录到全量导入：本项目实际学习路径

下面记录我们真实走过的路径。你不需要背命令；每一步更重要的是理解“它连接了什么、改变了什么、如何验证”。

### 10.1 先分清三个对象：服务器、客户端和项目环境

- **MySQL 服务器**：真正保存数据库和表的后台服务。它可以一直运行，不等于你已经登录。
- **MySQL 客户端**：终端里的 `mysql` 程序，负责把你的命令发送给服务器。
- **项目虚拟环境**：TradeIntel 的 `.venv`，用于运行 Python 导入脚本；它和 MySQL 账户不是一回事。

提示符可以帮助判断自己在哪里：

- `ye@电脑 %`：普通终端；
- `(.venv) ye@电脑 %`：普通终端，同时激活了 Python 虚拟环境；
- `mysql>`：已经进入 MySQL 客户端，可以输入 SQL。

SQL 只能在 `mysql>` 后输入。之前把 `SELECT ...` 输入到 `%` 后面时，终端出现 `function function function>`，只是普通 shell 在等待补全，并不代表 MySQL 出错；按 `Control + C` 可取消。

### 10.2 第一种方式：手动登录

```bash
mysql -u root -p
```

这里：

- `mysql` 是客户端程序；
- `-u root` 指定 MySQL 用户名为 `root`；
- `-p` 表示“随后隐藏输入密码”，不是把密码写在命令行上。

输入密码后出现 `mysql>`，就说明登录成功。可以用下面的 SQL 检查账户和版本：

```sql
SELECT USER(), CURRENT_USER(), VERSION();
```

退出客户端：

```sql
exit
```

**重要澄清：`mysql -u root -p` 本身没有错。** 我们实际就是用它成功登录的。它适合人手动操作，但每次都需要人在提示符中输入密码，因此不适合让 Python 脚本自动重复运行。不要使用 `-p你的密码` 这种写法，因为密码可能出现在终端历史或进程列表中。

### 10.3 第二种方式：保存本机登录路径

先在普通终端（不是 `mysql>`）执行：

```bash
mysql_config_editor set --login-path=tradeintel \
  --host=localhost --user=root --password
```

它会在本机的 MySQL 专用配置中保存一个名为 `tradeintel` 的登录路径。密码不会写进项目文件、Git 或命令行；以后脚本只引用这个名称：

```bash
mysql --login-path=tradeintel -e "SELECT USER(), CURRENT_USER(), VERSION();"
```

这个命令会执行一次查询并自动退出，不进入 `mysql>` 提示符。

两种方式的区别如下：

| 方式 | 典型命令 | 最适合 | 局限 |
|---|---|---|---|
| 手动登录 | `mysql -u root -p` | 人临时检查、学习 SQL | 每次需要交互式输入密码 |
| 登录路径 | `mysql --login-path=tradeintel` | Python 脚本、重复查询、批量导入 | 需要先在本机配置一次 |

因此，我们不是因为第一种方式“不能用”才换第二种，而是：第一种负责确认账户和学习，第二种负责让项目安全、可重复地运行。之前出现 `using password: NO`，原因是登录路径里还没有保存密码，并不表示 `root` 用户名错误。

### 10.4 建立数据库和三张表

先回到项目目录：

```bash
cd /Users/ye/dev/projects/TradeIntel
```

执行建表文件：

```bash
mysql --login-path=tradeintel < db/schema.sql
```

这里的 `<` 是普通终端的文件重定向：把 `schema.sql` 的内容交给 MySQL 客户端执行。文件中的核心动作是：

1. `CREATE DATABASE IF NOT EXISTS tradeintel`：数据库不存在才创建；
2. `USE tradeintel`：后续表都放进这个数据库；
3. `CREATE TABLE IF NOT EXISTS`：三张表不存在才创建。

它不会默认 `DROP` 数据库，也不会默认清空表，因此可以安全地重复执行。三张表分别是：

- `policy_event`：一行一项政策；
- `policy_product`：一行一项政策中的一个 HTS8 商品，通过外键连到政策；
- `trade_monthly`：一行一个“月份 × 原产国 × HTS10”贸易观察值。

查看表是否创建成功：

```bash
mysql --login-path=tradeintel -e \
  "USE tradeintel; SHOW TABLES;"
```

### 10.5 先导入一个月：验证字段和关联

贸易 CSV 使用 `LOAD DATA LOCAL INFILE` 批量传给 MySQL。这个功能有两道开关：客户端要允许，服务器也要允许。我们的导入脚本已经带了客户端选项；本机服务器默认是 `OFF`，所以导入期间临时执行：

```bash
mysql --login-path=tradeintel -e \
  "SET GLOBAL local_infile = ON;"
```

然后先导入 2018 年 7 月的单月文件，而不是直接处理 305 MB 的全量文件：

```bash
.venv/bin/python scripts/load_mysql.py \
  --login-path=tradeintel \
  --panel data/processed/trade/monthly/trade_import_2018_07.csv
```

脚本同时导入 1 条政策事件、818 个政策商品和单月贸易记录；如果表已经有数据而没有明确写 `--replace`，脚本会停止，这是为了防止重复导入。

### 10.6 用十条查询验证小规模结果

```bash
mysql --login-path=tradeintel tradeintel < db/verification_queries.sql
```

这些查询不是“为了多写 SQL”，而是分别检查：表行数、政策信息、外键孤立记录、月份范围、组合主键重复、政策商品匹配、目标国家金额、前后时期金额、国家排名和来源哈希。

小规模结果中，政策商品孤立数为 0，贸易表有 36,531 条记录，CSV 与 MySQL 的行数和金额总额一致。

### 10.7 小规模通过后，再导入完整面板

确认数据库中只有我们刚才建立和导入的验证数据后，才使用：

```bash
.venv/bin/python scripts/load_mysql.py \
  --login-path=tradeintel \
  --replace
```

这里的 `--replace` 会清空本项目三张目标表，再导入默认的完整 48 个月 CSV。它不是日常随便使用的选项；如果数据库中有其他人的数据，不能直接运行，必须先确认目标和备份策略。

全量导入完成后，关闭刚才临时打开的服务器开关：

```bash
mysql --login-path=tradeintel -e \
  "SET GLOBAL local_infile = OFF;"
```

### 10.8 最后的对账：证明迁移没有改变事实

不能只看“导入成功”这句话，还要把 CSV 和 MySQL 的关键摘要逐项比较：

- 行数：CSV 和 MySQL 都是 1,600,952；
- 金额总额：两边都是 1,716,137,643,878 美元；
- 月份范围：两边都是 2016-01 至 2019-12，共 48 个月；
- 组合键数量：两边都没有重复；
- 来源哈希：全部符合 SHA-256 格式；
- 政策商品外键：没有孤立记录。

这一步的核心思想是：数据库不是凭空产生新数据，而是把已经验证过的 CSV 放进一个带规则的容器。只要关键摘要一致，才可以继续在数据库上做分析。

### 10.9 这条流程中 AI 和你各自负责什么

AI 可以起草命令、建表文件、导入脚本和验证查询，也可以批量处理 160 万行数据。你需要判断：当前提示符是否正确、每一步是否会写入或清空数据、表的一行代表什么、验证数字是否符合业务含义。你的学习重点不是背 SQL，而是能解释数据流和发现不合理结果。
