# Phase 10u：用GLM-4.6V做三题诊断

新入口指定`glm-4.6v`，沿用原来的智谱API Key。只跑商品计数、缺信息、德国原产地这三道开发题，各一次，最多3次请求。模型不能执行数据工具。

## 为什么只跑三题

上一批12题都失败，但没有模型正文，无法判断是输出格式还是内容问题。现在优先取得可诊断证据：保存HTTP返回正文、模型回答、解析结果及阶段。商品计数测试明确任务，缺信息测试主动澄清，德国测试是否偷偷替换国家。

保持原提示和解析规则，只切换模型，便于定位差异。三题做对也不足以宣布新模型已通过项目验收。

## 你现在怎么运行

在终端复制：

```bash
cd /Users/ye/dev/projects/TradeIntel
.venv/bin/python scripts/run_glm46v_diagnostic.py --execute
```

程序先显示预检与模型名。提示输入Key时，粘贴原来的智谱Key后回车；隐藏输入不会出现字符，这是正常的。已有`TRADEINTEL_MODEL_API_KEY`环境变量时会直接使用它。

随后显示1/3至3/3的进度，结束时显示状态和文件路径。结果保存在`tmp/glm46v-diagnostic/`。你只需告诉我“运行好了”，我可以读取本地结果，无需粘贴Key或整份正文。

遇到调用异常立即停止，失败请求也计入3次上限。中断会保存已收到的记录；不自动重新发送尚不清楚是否完成的请求。若进程被强制杀死，逐行日志仍可用于诊断，但汇总文件可能未完成。

## 怎样看最后的状态

| 状态 | 意思 |
|---|---|
| collected_not_scored | 三题收集结束，还要审查内容 |
| stopped | 遇到异常或额外工具调用，已经停止 |
| interrupted | 被终端中断，已保存当时进度 |
| json_decode | 模型正文不符合严格JSON，原文已保留 |
| candidate_validation | JSON可读，但字段或原文依据不符合规则 |
| valid_proposal / valid_clarification | 通过格式校验，语义是否正确仍需审查 |

## 学习重点

Key识别账户，请求中的model选择模型，所以换模型不用新建Key。截图显示GLM-4.6V专用包尚有600万tokens，但具体使用哪份包、剩多少额度，应看平台账单；本地用量记录不能证明实际抵扣来源。

新的测试覆盖了模拟HTTP返回→解析→落盘→离线重放，能发现上一版“失败后正文丢失”的问题。模拟调用测试通过仍然不能代表真实GLM效果好，下一步要检查这三份实际输出。
